## 1. 游戏是什么

《静夜标记》是**去掉自由发言的狼人杀**：玩家不再说话，而是通过放「标记」公开表达身份判断，再投票放逐。

- **标记阶段**（替代发言）：按座位顺序，每人公开提交 1 个**身份声明标记**（给自己）+ 2~4 个**评价标记**（给他人），每个标记必须带理由（4 个通用理由 + 2 个职业专属理由【查验结论】【用药结果】）。
- **评价标记数量**随存活人数动态变化：4~6 人 2 个 / 7~9 人 3 个 / 10 人以上 4 个。
- **夜晚**：守卫 → 狼人 → 女巫 → 预言家 → 守墓人 依次行动，只公布死者不公布身份。
- **投票**：全员同时投，平票无人出局，结果公开。
- **随身物品/遗物**（可选模块）：开局随机发物品（月光石=被夜间行动造访次数 / 天平徽章=左右邻座是否同阵营 / 猎犬哨=死亡时存活狼人数），存活时看不到内容，死亡后转为遗物向全体公开 —— 这是本作最有辨识度的设计（信息不对等）。
- 胜负：好人杀光狼；狼人达成屠边（神职全灭或平民全灭）。

**为什么适合 QQ 群**：它本来就是「零语言门槛」的设计目标，用户输入被压缩成固定结构的标记操作，天然适配群聊机器人；「不说话」反而消掉了 QQ 群最难的语音/长文本协调问题。

## 3. QQBot 侧能力对照

已有的、可以直接用的原语（见 `docs/03-core-api.md`）：

- `session.whisper` / `session.ask(qq_id, group_id=None)` — 私聊发牌与收密令
- `session.broadcast(at=[...])` — 群内公开播报 / @ 当前行动者
- `session.choose` — 编号菜单（标记选项、理由选择）
- `session.wait_any(from_players=[...])` — 只接受指定玩家的群内发言
- `session.delete_message` — 撤回（可用于「群内提交后立刻撤回」的降级方案）
- `session.send_forward` — 合并转发（标记历史回顾）
- `ctx.state` — JSON 可序列化的对局状态（自动持久化）
- ~~`core.render` / `render_text_card` — 结算战报出图~~ **【已修正】** `core/render.py` 是**纯文本**排版库（`text_card`/`menu`/`list_card`/`result`/`paginate`），**不存在 `render_html` / `render_text_card` / `image()`**。要出图必须自研 PIL（参考 `src/plugins/games/aoe3_battle/bracket_renderer.py`）+ `MessageSegment.image` + `session.broadcast_rich`。`docs/03-core-api.md:321-343` 记的三个 API 是设计稿，未实现
- `core.llm` + `scene` — AI 补位与裁判文案
- 经济系统 `GameBase.award` — 胜负发奖

**近邻先例：`deep_sea_mission`**（3116 行）已经跑通了本作需要的两个最麻烦的模式：

1. **报名房间**：`@我 深海任务 8` → `@我 加入` / `@我 离开` / `@我 开始`，还带 `@我 重复加入` 的单账号调试座位；房间命令用 `rule=to_me() & _PENDING_ROOM` 在无房间时不拦截其他游戏。
2. **私聊发私密信息 + 失败即劝退**：私聊失败去 `WhisperFailedError`，点名提示并结束本局。

这两块可以近乎照搬。

## 4. 逐项映射（哪些保真、哪些必须降级）

| # | 静夜标记机制 | QQ 版方案 | 结论 |
|---|---|---|---|
| 1 | 私密身份牌 | `whisper` 发身份 + 座位号 | ✅ 保真（需加好友） |
| 2 | 夜晚各角色依次行动 | 按 `NIGHT_ACTION_ORDER` 顺序 `ask` | ✅ 保真 |
| 3 | **狼人同时行动 + 实时看到队友选择** | 降级为**依次**私聊收集；每次告知「当前队友意向：X」 | ⚠️ 失去实时性 |
| 4 | 真人在线时**不设超时**，仅断线 60s 兜底 | 必须**全员设超时**（建议夜间 60s / 标记 120s / 投票 60s），超时走默认行动 | ⚠️ 必须改造（可直接复用源项目的 `submitDisconnectedFallback` 兜底逻辑） |
| 5 | 标记阶段按座位顺序提交并即时公开 | 群内 `@` 当前玩家，一条消息提交「身份声明 + N 个评价标记」 | ✅ 达成，但**要重新设计输入语法** |
| 6 | 标记公开 / 历史可回顾 | `broadcast` + `send_forward` 或出图 | ✅ 保真 |
| 7 | 全员同时投票、结果一次性公开 | 依次私聊收集，收齐后群内统一公布 | ⚠️ 失去「同时感」，但结果一致 |
| 8 | 触发链（白痴免疫 / 白狼王带人 / 猎人开枪 / 骑士决斗） | 顺序 `ask` + 超时默认「不操作」 | ✅ 保真 |
| 9 | 物品 → 遗物公开、信息不对等 | `ctx.state` 记录 + 死亡时群内播报遗物 | ✅ 保真 |
| 10 | 6 位房间号 + 多房间并存 | **降级为「一群一局」**（`GameRunner` 按 `group_id` 唯一） | ❌ 不可保真 |
| 11 | 断线保留位 60s 可重连 | QQ 无「重连」概念 → 超时兜底 | ❌ 不可保真 |
| 12 | 房主自定义角色 / 物品 / 遗言开关 | 报名房间阶段分步 `choose` | ✅ 达成 |
| 13 | React UI（席位环、面板、结算页） | 文本卡片（`render.text_card`）+ 分页 + `send_forward`；出图需自研 PIL，列为可选增强 | 🔁 重做（工作量在文案设计，不在代码） |
| 14 | AI 玩家补位（`room:addAI`） | 用 `core.llm` 重写，比源项目更简单 | 🔁 可移植，建议第 2 阶段 |
| 15 | 警长系统 | 源项目也未实现 | — 不做 |

## 5. 风险与阻塞点

**P0 · 硬依赖：私聊**

夜间行动（守卫/狼/女巫/预言家/守墓人）与放逐投票必须私密，只能用私聊。这意味着：

- **每个玩家都要先加机器人好友**，否则本局无法开（沿用深海任务的「点名提示 + 结束本局」策略）。
- QQ 对私聊有风控，一局 4~6 人 × 若干轮的私聊频率需要在实测中观察。
- 「群内提交 + 立刻撤回」只能作为可选降级开关，**不能**作为默认（撤回有竞态，其他人可能已经看到）。

**P1 · 节奏**

web 版一局 10~15 分钟靠 Socket.IO 实时推送；QQ 版每次交互是一次消息往返。粗算 4 人局 3 轮：标记 4×3=12 次 + 投票 4×3=12 次 + 夜间约 9 次 + 触发若干 ≈ **35~45 次往返**。按每次 10~20 秒，一局约 **8~15 分钟**。可接受，但必须配好超时兜底，否则一个挂机玩家会拖死全群。

**P2 · 消息量与格式**

- 单条 ≤ 2000 字、连发间隔 ≥ 500ms（`broadcast` 已节流）。
- 标记历史的完整回顾必须走 `send_forward` 或图片，否则刷屏。
- **标记输入语法是本次移植的核心设计决策**（直接影响 CLI 一致性铁律），建议形如
  `身份 好人 直觉 | 3 狼人 投票分析 | 5 好人 直觉`
  并同时提供编号菜单式引导作为新手路径。**必须一次性定死，CLI 与 Bot 共用同一套解析函数。**

**P3 · 状态与持久化**

- `ctx.state` 必须 JSON 可序列化：源项目用 `userId: string` 作 key，QQ 侧是 `int` 的 `qq_id`，**JSON 往返后 dict key 会退化成 str** —— 必须统一在状态里只用 str，或在读写时统一转换，否则会出现「找不到玩家」类隐性 bug。
- 服务器重启会 `abort` 所有活跃对局（`recover_active_sessions` 目前是保守策略）。一局十几分钟的窗口内概率低，属可接受损失，但要在结束文案里说清。

**P4 · 移植保真度**

触发链（白痴免疫 → 白狼王带人 → 猎人开枪，含「被毒不能开枪」等细则）与夜晚结算（同守同救同归于尽）是最容易写错的部分。`rules.ts` 与 `game/__tests__/p0Rules.test.ts` 是权威来源，建议**先原样转成 Python 单测**再写状态机。

## 6. 工作量估算

参考：`deep_sea_mission` 3116 行 Python 是一个完整多人游戏（含战役）。

**阶段 A — 可玩 MVP**（建议先做这个）

- `rules.py`：胜负 / 夜晚结算 / 投票结算 / 标记合法性（从 `rules.ts` 直转）≈ 200 行
- `roles/`：狼人、预言家、女巫、猎人、守卫、平民 ≈ 350 行
- `game.py`：状态机（夜晚顺序 → 结算 → 标记 → 投票 → 触发链）≈ 900~1300 行
- `commands.py`：报名房间（照搬深海任务模式）≈ 200 行
- `config.py` / `prompts.py`（结算文案）/ `models.py`（可选战绩表）
- `scripts/cli_adapters/silent_mark.py` + `play_cli.py` 注册 ≈ 500~800 行（**铁律，不可省**）
- `docs/games/silent-mark.md` + `README.md`
- 合计 **约 2500~3500 行 Python**

**阶段 B**：物品/遗物系统（月光石 + 天平徽章 + 猎犬哨）、剩余 4 个角色（守墓人/白痴/骑士/白狼王）、9~12 人局、结算出图、经济发奖。

**阶段 C**：AI 补位（`core.llm` 重写源项目 2242 行的决策子集）≈ 600~900 行 + prompts。**QQBot 侧比 web 版更容易做**，因为已有统一 LLM 网关，且能一次性解决「4 人局凑不齐人」的落地难题。

## 7. 建议

1. **可以立项，但按阶段 A 起步**，先做 4 人局闭环（1 狼 + 守卫 + 女巫 + 1 平民）。4 人局规则最紧、角色最少、一轮就能验证全部状态机分支。
2. **第一件事是定死标记输入语法**并写进 `docs/games/silent-mark.md`，CLI 与 Bot 共用同一个解析函数（`13-cli-bot-parity.md` 铁律）。
3. **第二件事是把 `rules.ts` + `p0Rules.test.ts` 转成 Python 单测**，把结算细则锁死，再动状态机。
4. 报名房间、私聊发牌、私聊失败劝退三块**直接从 `deep_sea_mission` 抄**，不要重新发明。
5. 明确写进玩法说明：**所有玩家需先添加机器人为好友**，否则无法开局。
6. AI 补位放在最后，但它才是这个游戏在 QQ 群里真正能常态化跑起来的关键。
