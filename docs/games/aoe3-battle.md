## 一、玩法概述

### 模式 A：押注模式（首期实现）

1. 玩家 `@机器人 斗蛐蛐` 开一局
2. 系统在等资源预算下随机生成**红蓝两方阵容**，公布对阵面板
3. **押注阶段**，群友发押注口令下注
   - **统一口令**：`押注1`（押红方）/ `押注2`（押蓝方）
   - 数字口令的好处：避免颜色识别歧义、容错率高、便于扩展（未来如做多方混战可直接 押注3 / 押注4）
   - **面板视觉**仍用 🔴红 / 🔵蓝（颜色直观），但口令只接受 1/2，不再兼容
   - **不设倒计时**：群友可随时押注，任意群友发 `开战` 命令即可跳过等待直接开打
   - **锁死第一笔**：同一玩家押注后不可改押（发了 `押注1` 再发 `押注2` 无效）
4. 进入战斗阶段后**不再接受押注**
6. 系统**一次性完整模拟战斗**，得到完整事件流，再**按时间分批播报**
7. 结算：赢家平分输家的金币池,所有参与者获得 1 金币参与奖
8. **不自动开下一局**（与项目内其他游戏一致，由玩家手动发起）

### 模式 B：单挑模式（首期一起做）

1. 玩家 `@机器人 斗蛐蛐 单挑` 开一局
2. 系统随机抽两个兵种（包含无费用兵种），**真正的 1v1**：每方**只有 1 个单位**
3. 同样可押注，规则同模式 A

### 通用设置：交火距离

- `@机器人 斗蛐蛐 交火距离 远`：双方阵型前沿中心间距为 **36**，未设置时的默认值。
- `@机器人 斗蛐蛐 交火距离 近`：双方阵型前沿中心间距为 **3**，用于快速接敌。
- 该设置和默认预算、默认时代一样，按群持久保存，只设置、不立即开局。
- 后续本群所有斗蛐蛐模式读取该设置，包括押注、单挑、乱斗、指定兵种、王中王、锦标赛和国战。
- 开局图与文本兜底会标明本局是「远距交火」还是「近距交火」。
- 近距 3 为严格中心间距；彩蛋/超大单位若因此出生重叠，不额外做尺寸补偿。

### 模式 C：乱斗（已实现）

1. 玩家 `@机器人 斗蛐蛐 乱斗` 开一局
2. 系统从 `BATTLE_BLACKLIST`（彩蛋 / 作弊码 / 怪物级战役兵 ~18 个）随机抽阵容
3. **完全无视 cost，按战力分平衡数量**——详见 §2.4
4. 押注 / 战斗 / 结算流程完全复用模式 A
5. **节目效果优先于公平**：怪兽 vs 民兵就是悬殊，独苗 vs 几只小弟也照样看戏

### 模式 D：王中王（已实现）

> 对外名称 **王中王**；内部 `GameMode.id = "rival"`。  
> 从固定 **10 个职能主题** 里抽兵对决，主题用 tag 并集/交集筛池（详见 §2.5）。

#### 入口 A：表情选主题（主路径）

1. 玩家 `@机器人 斗蛐蛐 王中王`
2. **尚未开局**——进入「选主题」阶段，**不占用** `GameRunner` slot
3. 系统从 10 个主题中 **随机抽 3 个**，发一条选单消息
4. 为该消息挂载 **3 个表情**（NapCat 消息表情回应）；群友 **点击表情** 即选定对应主题
5. **任一群友点选即生效**（第一个有效表情回应锁定主题），随后 **正式 `create_and_start` 开局**
6. **不设倒计时**：群友可随时点选；`@结束` 可取消 pending
7. **文字兜底**：对同一条选单消息回复 `1` / `2` / `3` 等价于点第 1/2/3 个表情（CLI 同样用 1/2/3，见 `docs/13-cli-bot-parity.md`）

#### 入口 B：指定主题（快捷）

1. 玩家 `@机器人 斗蛐蛐 王中王 散兵`（或 `火枪`、`近战骑` 等主题别名）
2. **跳过选主题**，直接用该主题开局
3. 可选末尾预算数字：`斗蛐蛐 王中王 散兵 15000`（范围 1000~50000，默认 10000）
4. 默认预算可在群里持久设置：`斗蛐蛐 预算 15000`（范围 1000~50000，所有群友可用）

#### 对阵与后续流程

- 红蓝双方各 **随机 1 个兵种**（均从该主题池抽取），数量用 **LCM 平衡资源**——与指定兵种对决（2 个指定兵）逻辑一致，不是单挑 1v1
- 押注 / 开战 / 模拟 / 结算 **完全复用模式 A**
- VS 面板标题示例：`⚔️ 帝国3斗蛐蛐 · 王中王 · 散兵王`

### 模式 E：指定兵种对决（已实现，简述）

- `@机器人 斗蛐蛐 兵种A 兵种B [预算]`
- `@机器人 斗蛐蛐 兵种A 数量 兵种B 数量`（固定数量，每方 1~1000）
- 未指定数量时继续使用 LCM 资源平衡；指定后严格使用玩家数量，时代改良不改变数量
- 详见 `lineup.py :: generate_custom_lineup`

### 模式 G：国战

入口为 `@我 斗蛐蛐 国战`；也可写 `@我 斗蛐蛐 国战 文明A 文明B [预算] [3-5时代]`。
随机模式从 24 个可玩主文明中抽取两个不同文明，默认 3 时代。

#### 文明池与升级

- 只用 `seeds/aoe3/civs.json` 的 `_meta.curated_civs`，不纳入革命、战役文明、原住民部落或盟友单位。
- 普通斗蛐蛐继续使用不带文明上下文的 `unit_upgrades.json`。
- 国战额外使用 `civ_unit_upgrades.json`，按文明应用皇家护卫及 Honored / Exalted / Champion / Legendary 等文明升级。
- 文明覆盖可修改血量、攻击、名称、射程、射速、速度、护甲、倍率和单位成本。
- 国战只开放 3 至 5 时代，避免低时代无法形成完整编制。

#### 正规军池

候选先通过普通战斗池过滤，再排除英雄、探险家、侦察兵、宠物、纯治疗者，以及炸药筒、隐匿炸药筒、攻城槌等专职爆破单位。
村民、建筑、船、占位符、战役单位、彩蛋和怪物不入池。

佣兵、亡命徒和领事馆远征军属于合法军力。领事馆单位需有正常资源费用，且不能是 `AbstractBannerArmy` 代币。
间谍、密探等 `MercType2 + AbstractCanSeeStealth` 单位与印度 `*mansabdar` 强化单位单独排除。

#### 科技体系

国战科技采用四层结构，文明归属、通用池资格、本局命中和最终应用互不混用：

1. **原始游戏数据**：`data/aoe3/raw/` 下的 `civs.xml`、`techtreey.xml` 与该文明 `homecity*.xml`，只读。
2. **文明可获得科技**：`scripts/crawler/aoe3_civ_available_techs.py` 从文明 `agetech` 递归展开 `TechStatus active/obtainable`，再合并该文明主城文件的 `cards/card/name`，输出 `seeds/aoe3/civ_available_techs.json`。文明归属不使用单位目标、单位标签或 `unique_techs` 反推。
3. **文明通用池**：`scripts/crawler/aoe3_civ_war_tech_pool.py` 从文明可获得科技中排除时代升级和革命卡，保留战斗或成本科技，并仅保留可能作用于国战参战单位类型的条目，输出 `seeds/aoe3/civ_war_generic_techs.json`。革命卡指 id 前缀 `DEHCREV` / `DEREV`，或带 `RevoltTech`。村民、建筑、船只、英雄、守卫、宠物、场景与经济单位科技不入池；佣兵、亡命徒和领事馆单位属于合法目标。配兵自选、配兵预定义、配兵空位 AI 与国战自动编制共用这套池、摘要和结算。
4. **本局筛选与应用**：`src/plugins/games/aoe3_battle/civ_war_techs.py` 从该文明通用池中筛出能命中当前组合参战兵的科技，再按固定优先级选择，不随机。

科技来源分为：

- `seeds/aoe3/civ_war_priority_techs.json`：人工确认的质变/机制科技，分为 `core` 与 `support`。
- 文明通用池：普通兵种战斗力科技与成本科技。

应用规则：

- 人工优势策略优先使用 `required_tech_ids`；若未配置必选科技，则从文明通用池补 1 条命中当前组合的科技。
- 自动组合获得 `N - 1` 条科技：二兵种 1 条，三兵种 2 条；一兵种不补偿。
- 先筛选出本局能命中参战兵的科技，再抽取，不允许先抽取后判定导致名额浪费。
- 同一科技可命中多个兵种或多套组合，但对同一组合只作用一次。
- 时代升级由 `apply_upgrades()` 按文明和时代独立应用，不进入可选科技池，避免重复叠加。
- 科技可拆分效果：战斗与成本效果生效，送兵、经济、人口、训练、建筑和解锁等伴随效果不生效；减价和增价如实参与数量分配。
- 应用顺序固定为：生成编制 → 应用时代升级 → 应用组合科技 → 数量重新分配 → 开屏。

展示：

- 国战开屏 PNG 在双方文明块显示实际科技摘要，最多两条，超出部分以省略号收束。
- 文本兜底和 VS 简报显示完整科技名。
- 配兵私聊完成页、锦标赛亮相和 VS 简报的国战科技行按“【生效兵种】科技名：人话效果”显示选中科技；无法可靠翻译的效果只显示科技名，不生成猜测说明。

#### 编制生成

单位按火枪、散、冲击、龙骑、近战反骑重步、反步兵炮六类生态位映射，一个单位可兼任多个生态位。
每个文明先生成具体单位与资源配比的候选编制，再进入随机选择；不会直接随机拼兵。

通用骨架为火枪马、龙骑散、散马、火枪炮、龙骑炮、火枪散、重步散，以及固定三兵种扩展等。

当前资源比例为正式运行口径：

| 编制 | 按槽位顺序的资源占比 |
|---|---|
| 火枪马 | 火枪 60% / 冲击 40% |
| 龙骑散 | 龙骑 45% / 散 55% |
| 散马 | 散 60% / 冲击 40% |
| 火枪炮 | 火枪 70% / 炮 30% |
| 龙骑炮 | 龙骑 65% / 炮 35% |
| 火枪散 | 火枪 50% / 散 50% |
| 重步散 | 近战反骑重步 40% / 散 60% |
| 散龙炮 | 散 45% / 龙骑 30% / 炮 25% |

选择顺序：

1. 有优势策略时，按 50% 优势策略 / 50% 普通策略选择顶层类型。
2. 普通策略按 75% 纯本国 / 25% 混编来源选择；混编统一包含佣兵、亡命徒和领事馆兵，不允许纯外援。
3. 在当前来源可实现的战术中等概率选择策略，再选择具体单位与比例版本。
4. 双方独立选兵，不做强制五五开，也不排除镜像或正常天克。

每文明首版优势策略共 75 套，覆盖全部 24 个文明；中国旗军按原游戏固定单位数量比例生成。
国战开屏使用文明旗帜、优势策略、兵种图标与数量组成图片，发送失败时降级为精简文本。

### 模式 H：配兵与配兵锦标赛（已实现）

入口：

- `@我 斗蛐蛐 配兵`：一场 1v1，房间满员 2 人。
- `@我 斗蛐蛐 配兵锦标赛`：8 人单败淘汰，房间满员 8 人。

发起的人占用第一个席位，但没有任何房主身份或特权。房间阶段使用 `加入`、`离开`、`开始`、`开战`、`结束`；人满后拒绝继续加入。任意群友都可以发 `开始`，只在所有已报名玩家完成私聊配兵后执行。开始前可以私聊回复「重来」重配，或先 `离开` 再加入。发起人 `离开` 只是退出自己的席位，房间仍有玩家时继续；最后一人离开后房间自动解散。报名与加入都要求玩家已经加机器人为好友。

从开房到本局结束，本群不能同时再开另一局斗蛐蛐。开始时空位补 AI：

- 配兵补到 2 人；配兵锦标赛补到 8 人。
- AI 在开始时生成一次国战自动编制，之后不换兵；每场仅按冻结预算重新计算人数。
- AI 文明从 24 个可玩主文明随机，允许和玩家重复。

预算、时代和交火距离沿用本群斗蛐蛐设置，在 `开始` 时冻结。本群时代不在 3～5 时不能开房。此模式没有押注。

#### 私聊配兵

配兵只通过机器人私聊完成，群里只保留房间状态、亮相和战斗结果。候选以序号列出。

1. **国家**：玩家指定文明或让系统随机；池与国战相同，只用 24 个可玩主文明。
2. **军队**：二选一。
   - 预定义阵容：使用文明已有的国家战术，连同兵种、资源分配和绑定科技整套采用。
   - 自己配：从本局时代可出的该文明国战正规军中按顺序选择 1～3 个兵种，不能重复；每个兵种至少要能买 1 个。
3. **侧重**：自选超过一个兵种时，按兵种顺序输入同样个数的正整数权重。只选一个兵种时，整笔预算全部用于该兵种。
4. **科技**：自选兵种时，从能作用于出场兵种的文明科技中选 1～2 条。每一条先写本阵容里吃到它的兵种，如「【诸葛弩】」或「【诸葛弩、火枪兵】」，再写「科技名：人话效果」，并标注专属或通用；翻译不出效果时只留科技名。确认页和战报用同一句。预定义阵容使用自己的绑定科技，不进入这一步。

自选权重先归一为目标占比，再按国战现有资源分配算法分配：

1. 每个兵种先分配 1 个；买不起则编制不合法。
2. 有余量时，每次给一个买得起的兵种增加 1 个，选择增加后实际花费占比与目标占比平方误差最小的兵种；误差相同则买更便宜的。
3. 直到再增加任何兵种都会超预算。

科技只改变战斗属性，不改变买兵人数。送兵、经济、人口、解锁和建筑效果不进入可选池。可选科技必须同时属于该文明、处于本局时代，并能命中阵容中的出场兵种；一条都命中不了时要求玩家改选兵或改用预定义阵容。

预定义阵容使用自身的 `resource_shares` 或 `fixed_ratio`，不读取玩家权重。阵容保存兵种顺序和权重，每场都按 `开始` 时冻结的预算重新计算人数。

#### 赛制

名单锁定并完成配兵后先亮相；任何人发 `开战` 后按普通斗蛐蛐完整模拟、按时间播报并结算。

配兵锦标赛与王中王锦标赛使用相同的单败淘汰加败者组排位结构，共 12 场，排出 1～8 名：

```text
八强 4 场 -> 败者组排位 2 场 -> 7/8 名战 + 5/6 名战
-> 半决赛 2 场 -> 季军战 -> 决赛
```

同一轮内的比赛连续完成，一轮结束后发 `开战` 推进下一轮。八强配对随机。单场平局仍按普通斗蛐蛐记录；锦标赛需要晋级时，剩余总生命更高的一方晋级，相同则随机晋级并在战报中写明。

### 模式 F：王中王锦标赛

> 对外名称 **王中王锦标赛**；内部 `GameMode.id = "rival_tournament"`。  
> 从同主题池抽 **8 种兵**，单败淘汰 + 败者组排位，完整排出 1~8 名。

#### 指令

```
@机器人 斗蛐蛐 锦标赛
```

- **主题选择流程与普通王中王一致**：开局后先随机 3 主题、表情/文字选主题
- 主题同王中王（散兵/火枪/近战重步/弓手/掷弹/近战骑/远程骑/炮/亡命徒/佣兵）
- 8 个不同兵种随机抽签，进行 12 场单败淘汰与排位赛
- 每场双方各使用 1 个兵种，按现有 LCM 规则平衡数量；平局时剩余血量更高的一方晋级，剩余血量相同则随机晋级
- 群聊押注阶段可用序号 1-8 押注夺冠；CLI 同一流程用序号押注
- 群聊阶段结果发送对阵图，决赛结束后发送最终排名；CLI 使用等价文本结果
- 不支持自定义预算和时代（锁定群配置）

#### 赛制

单败淘汰 + 败者组排位，共 12 场比赛：

```
QF1/2/3/4（4 场）→ LR1/LR2（2 场排位）→ 7/8名战 + 5/6名战（2 场）
→ SF1/SF2（2 场半决赛）→ 季军战 → 决赛
```

#### 阶段流程（4 阶段出图 + 最终排名）

| 阶段 | 内容 | 出图 | 交互 |
|------|------|------|------|

#### 2.2.3 v2 复合阵容（已实现）

每方可出 **1~3 个兵种**，系统随机抽取 + 自动分配数量。红蓝双方**独立生成**（兵种数可以不同）。

##### 兵种数量权重

```python
slot_count = rng.choices([1, 2, 3], weights=[45, 35, 20], k=1)[0]
# 1 种兵 45%（最常见，保持经典单兵种对决的频率）
# 2 种兵 35%（主力+辅助的经典搭配）
# 3 种兵 20%（偶尔出现的豪华阵容）
```

红蓝双方各自独立抽取兵种数，互不影响（可能出现红方 1 种 vs 蓝方 3 种）。

##### 抽兵约束

抽到的 N 个兵种必须满足：**各出 1 个的总 cost ≤ 该方预算**，否则重抽。

```python
# 例：预算 1000，抽到 鹰炮(600) + 铁甲舰(800) + 护卫舰(1000)
# 保底消耗 = 600 + 800 + 1000 = 2400 > 1000 → 重抽
```

这保证了后续贪心填充算法的"每种保底 1 个"前提安全。

##### 多兵种资源分配：贪心填充三步法

```
算法：GreedyFill(budget, unit_costs[])
──────────────────────────────────────
输入：总预算 budget，兵种 cost 列表 unit_costs（已通过抽兵约束）
输出：每个兵种的数量 counts[]

Step 1 — 保底：每种兵各 1 个
  counts = [1, 1, ..., 1]
  remaining = budget - sum(unit_costs)

Step 2 — 均分：剩余预算均分给每个兵种
  per_budget = remaining // N
  对每个兵种 i：
    extra = per_budget // unit_costs[i]
    counts[i] += extra

Step 3 — 贪心零头：最后的零头逐个加最便宜的兵
  remaining = budget - sum(counts[i] * unit_costs[i])
  while remaining > 0：
    找 cost ≤ remaining 的最便宜兵种，+1
```

**设计要点**：
- Step 2 的均分保证贵兵种也能分到合理数量（不会全被便宜兵吃掉）
- Step 3 的贪心只处理零头（通常 < 最便宜兵种的 cost）
- 无人口上限，数量完全由预算决定

#### 2.2.4 近似 LCM 算法（单兵种资源平衡）

双方都是 1 种兵时，使用近似 LCM 让双方资源尽量相等：

```
算法：ApproxLCM(cost_a, cost_b, base_budget)
──────────────────────────────────────────────
1. ca, cb = round(cost_a), round(cost_b)
2. lcm = LCM(ca, cb)
3. 如果 lcm > base_budget × 1.3：
     → LCM 太大，退化为 base_budget
4. 否则：
     actual = round(base_budget / lcm) × lcm
     actual = clamp(actual, base_budget × 0.7, base_budget × 1.3)
5. red_count = actual // ca
   blue_count = actual // cb
```

**预算浮动范围 ±30%**（不会偏离太远）。

#### 2.2.5 人口成本折算

单位人口占用房子槽位。AoE3 中 1 个房子 = 100 木 = 10 人口，即**每人口 ≈ 10 资源**。

#### 战力分公式（V2 几何平均 + 双层溢出减益）

```python
ARMOR_WEIGHT          = 0.3   # 护甲轻微增益（armor=0.9 仅 ×1.27）
BLACKLIST_AOE_DPS_MULT = 0.3   # AOE 单击伤害加成（每 1 半径 +30%）
HIT_BASELINE          = 50    # 单击伤害基准
DPS_BASELINE          = 20    # DPS 基准

def _soft_diminish(x, base):
    """x ≤ base 时线性；x > base 时按 sqrt 收益（边际递减）。"""
    return x if x <= base else base + sqrt((x - base) * base)

def power_score(unit):
    # HP：线性单调递增 + 护甲轻微增益
    hp_eff = hp × (1 + max(armor_r, armor_m) × ARMOR_WEIGHT)

    # 单击伤害（含 AOE 加成）先溢出减益（治"800 攻击打民兵"的浪费）
    hit_r = _soft_diminish(atk_r × (1 + aoe_r × 0.3), HIT_BASELINE)
    hit_m = _soft_diminish(atk_m × (1 + aoe_m × 0.3), HIT_BASELINE)

    # 除以 ROF 得 DPS，再做一次溢出减益（治"机关枪打蚊子"的浪费）
    dps_eff = _soft_diminish(max(hit_r/rof_r, hit_m/rof_m), DPS_BASELINE)

    # 几何平均：HP/DPS 同等加权，单项极端高不会让总战力线性爆炸
    return sqrt(hp_eff × dps_eff)
```

设计三要素（与玩家直觉对齐）：

1. **HP**：单调递增（恒成立），sqrt 让大血量不线性主宰；护甲只做轻微增益
   （旧公式 `1/(1-armor)` 在 armor=0.9 时放大 10 倍，纯虚高）。
2. **DPS**：由 atk/rof 计算，**双层边际递减**——单击 800 攻击对一个 hp 500
   的小兵浪费 300（高射炮打蚊子），公式按 sqrt 收敛而非线性贡献。
3. **几何平均**：HP 与 DPS 同等重要，单独极端值不会线性放大。

**只看模拟器实际使用的 `attack_ranged` / `attack_melee` 槽位**：

- `attack_siege` 是 BuildingAttack 系列（§3.9），模拟器不读，不计入。
- **倍率（multipliers）不计**——克制天然在战斗里发挥作用，加进战力分会高估。
- 不计 speed / 射程——1v1 静态战力公式无法量化"接战阶段"影响。

#### 实测标定（V2 公式 vs 模拟器实战）

| 1 镭射熊 = ? | 公式预测 | 模拟器实测均衡点 | 偏差 |
|---|---|---|---|
| 重型火炮(无人口) | 19:1 | 15:1 | 1.2× |
| 防卫据点加农炮 | 12:1 | 7:1 | 1.8× |
| 民兵长 | 55:1 | 30:1 | 1.8× |

跨档偏差从旧公式的 **几十~几千倍** 压到 **1~2 倍**。剩余偏差来自剪刀石头布
（armor 实际抵消、AOE 群体放大、射程接战节奏等），单兵静态公式无法覆盖。

| 等级 | 单兵分 | 代表 |
|---|---|---|
| 怪兽 | ~10500 | 垮盛顿 |
| 次顶 | ~2800 | 镭射熊 |

#### 数量分配：共用 anchor `max(双方 max) × r`

```python
SLOT_WEIGHTS_BLACKLIST = [50, 50, 0]    # 1/2/3 种兵的概率（黑名单池小，去掉 3 兵种）
BLACKLIST_R_MIN, BLACKLIST_R_MAX = 3.0, 6.0

# 抽兵（双方独立，无 cost 约束，不限制兵种组合）
red_units  = rng.sample(pool, rng.choices([1,2,3], SLOT_WEIGHTS_BLACKLIST))
blue_units = rng.sample(pool, rng.choices([1,2,3], SLOT_WEIGHTS_BLACKLIST))

# 共用 anchor：让两边都向同一个 target 配兵，总战力自然对齐
anchor = max(max(red_scores), max(blue_scores))
r = rng.uniform(R_MIN, R_MAX)
target = anchor × r

red_counts  = _fill_to_target(target, red_scores)
blue_counts = _fill_to_target(target, blue_scores)
```

`_fill_to_target` 策略：每种保底 1 个，然后反复挑 `counts[i] × scores[i]` 最小
的兵种 +1，直到总分 ≥ target × 1.05。"挑当前总分最小的 +1" 实现多兵种均匀
ramp。**无个体数上限**——与押注/单挑模式一致（§3.2），数量完全由战力分决定。

**关键决策**：

1. **共用 anchor**（旧版用本方 min × r）：旧策略下一方有怪兽就保底 1 只、
   弱方按本方 min ramp，跨方战力悬殊到 20~37×。共用 anchor 让两边都向同
   一个 target 配兵，跨方战力比压到 1~4×。
2. **无数量上限**：与押注/单挑同哲学——1 镭射熊 vs 500 民兵就是黑名单乱斗
   的常规节目效果。"超人打一堆蚂蚁"也是合法节目。模拟器在 §2.2.5 的压测
   已验证 500 个体 < 1 秒可控。
3. **不约束兵种组合**：保留"加藤大名 vs 镭射熊"这种荒诞局的可能性——克制和
   AOE 由模拟器自然发挥，公式不做事前过滤。

## 三、战斗模拟

### 3.0 模拟与播报的关系（重要架构决策）

**采用"先全量模拟、再分批播报"模式**：

```
押注结束 → [一次性完整模拟战斗，生成完整事件流] → [按时间窗分批吐日志]
```

- **优点**：模拟过程不受播报延迟干扰；播报失败可重试；测试可绕过播报直接看结果
- **播报节奏**：每 **2 秒模拟时间**（即 20 tick）汇总成一条消息发出
- **零伤亡片段**：该 2 秒窗口内**双方均无死亡**则**跳过**（不发消息也不 sleep，直接进入下一窗口），避免冷场刷屏
- **关键节点**：开战、首杀、半灭线、最后一击、战斗结束 单独成条优先播报
- **真实节奏**：有伤亡的窗口播报后 sleep 2 秒，让群友有时间看，节奏接近真实战斗

> **当前正式口径（2026-09-24）**：普通对局不再逐窗口播报，也不再发送开战提示。
> 当前流程为：
>
> 1. 开局发送一张通用开局图（国战复用国战开局图，其余模式使用无国家字段的通用开局图）。
> 2. 押注说明包含在开局图中；实际押注仍逐条简短确认。
> 3. 战斗过程静默；最终依次发送战场回放视频、完整文字战报、押注结算（无押注不发结算）。
> 4. 文字战报保留胜负、时长、剩余兵力/HP、战损资源、各兵种击杀与伤害，不再输出 `xxx 全灭`。
> 5. 没有流量或不想观看视频的群友必须能只靠文字战报获得完整结果；视频成功时也发送完整文字战报。
> 6. 回放生成失败或发送失败时，先发明确失败提示，再继续发送完整文字战报。
> 7. 回放编码临时文件自动回收；上传失败的文件保留 24 小时，受文件数和总容量上限清理。
> 8. 锦标赛每场仍输出一次文字战报；只有决赛录制并发送回放视频，其余轮次不生成视频。
>
> 以下 §8.2–§8.5 是旧逐窗口广播模型；CLI `--debug` 仍可能用于调试，正式群局不再调用。

#### 3.0.1 回放与展示实现边界

- 回放录制只保存公开展示字段；攻击和死亡事件额外保存事件发生时的攻击者/目标坐标，不读取战斗内部状态改变成败。
- 自适应倍速按真实事件密度分段：短局保持 1x，首次接敌、首次阵亡、重大伤亡和终局附近保持正常速度，长静默段最高 8x。
- 视频特效按压缩后的输出时间绘制。每个攻击、AOE、阵亡事件至少保留一个输出帧，终局采样必须包含 `output_duration`。
- 网页与视频使用同一份 `64x64 RGBA` 圆形兵种 icon 画布；查看器可缓存 PNG，但不得维护另一套缩放/裁切规范。
- 网页查看器消费真实 `ATTACK / AOE_SPLASH / DEATH` 事件，按事件身份去重、按 `expires_at` 过期。
- 查看器滑条是帧轴，不是连续时间轴；界面同时显示当前帧号和源时间。
- 开发网页以「自选阵容」为主路径：可分别选择红蓝文明的兵种、数量与科技；兵种用可搜索输入框（中英文名 + id 都能匹配），不靠长下拉挑选。「全兵种」勾选后，该方的选兵范围从文明正规军换成完整战斗池（含佣兵、原住民、亡命徒、英雄、宠物），文明仍决定可选科技与时代升级。「蓝方军费随红方自动平衡」勾选后，蓝方按所选兵种构成自动放大/缩到与红方军费相当。
- 原先的「快速单挑」标签页已并入「自选阵容」：「全兵种」覆盖了它的全池裸兵对拍能力，且额外支持科技与多兵种。
- 开发网页显示蓄力就绪/冷却状态与攻击动作名：画布用蓄力环标出就绪与冷却，右侧攻击日志可按「仅蓄力」过滤，选中单位可查看其全部可用攻击模式与当前动作。

### 3.1 场地模型

- **二维矩形场地**：x 轴是双方接近方向，y 轴是横向展开方向
- 单位保留现有 X/Z 两轴椭圆占位及朝向；X=Z 时退化为圆。当前未切换矩形，也未改变原有轴向与旋转标记语义。
- 双方按兵种射程与速度在各自半场展开阵型，近战优先进入前排
- 场地宽度和高度由 `field_length`、双方阵型规模与边距共同计算
- `field_length` 生产入口默认 36，本群设置“交火距离 近”时改为 3；该值直接决定双方最前排中心之间的初始距离。
- 距离使用二维欧氏距离；攻击、目标选择和 AOE 均基于二维位置
- 边界为硬约束，单位不会被弹飞或挤出场地

### 3.2 士兵个体

- 每个士兵有**独立 HP**、二维位置、速度、攻击 CD 与锁定目标
- 无人口上限，个体数完全由资源预算和兵种 cost 决定
- 每个个体参与碰撞、避让、绕行、攻击、死亡与统计
- 没有“接触容量”或“渗透”抽象；能否接敌由二维空间自然决定

### 3.3 时间推进

- 模拟以 **tick** 为单位推进（tick 间隔 0.1 秒）
- 每 tick 依次处理：空间索引更新 → 期望速度 → 局部避让 → 碰撞修正 → 目标锁定 → **同时开火结算** → 死亡清算 → 事件入队
- 不再按固定时长截断。连续 **10 秒**没有任何单位损失 HP 才超时，按**剩余单位总资源价值**判胜；单挑模式超时判**平局**。仍在造成伤害的战斗会继续，直到一方全灭或再次停火满 10 秒
- 模拟器输出**结构化事件流**（ATTACK / DEATH / TARGET_LOCK / AOE_SPLASH / BATTLE_END），话术层从事件流生成播报文本

#### 同时开火结算规则（核心，所有兵种通用）

每 tick 的攻击阶段采用**同时开火**模型，而非串行结算。此规则对远程、近战、炮兵一视同仁：

1. **收集攻击者**：所有 CD 好且已锁定目标的士兵，在本轮"出手"——攻击已发出，不可撤回（远程=弹丸出膛，近战=刀已挥出）
2. **进入 CD**：所有攻击者立即进入攻击冷却（ROF），不管后续结算结果
3. **随机顺序结算**：将所有攻击者（跨阵营）随机打乱顺序，依次结算伤害：
   - 命中时目标**还活着** → 正常扣血 + 触发 AOE 溅射
   - 命中时目标**已死**（被本轮其他人先打死） → 伤害浪费，**不触发 AOE**
4. **死了也能出手**：即使某士兵在本轮结算中被别人杀死，它的攻击依然命中（步骤 1 已标记）

**设计意图**：
- **火力浪费**：多人锁同一目标时产生 overkill，远程兵/炮兵天然更易浪费火力（射程远 → 更多人锁同一个前排目标），近战兵也会（多人围殴同一个敌人，第一刀砍死了后面的刀砍空）
- **消除先手优势**：不再因为 ID 小而先开火、先杀人，双方对等
- **AOE 不炸尸体**：命中活目标才触发溅射，打尸体不爆——避免 AOE 兵种获得不真实的溅射覆盖

### 3.4 移动规则

- 每 tick 使用空间哈希查询局部邻居，避免全战场两两扫描
- 单位先朝最近可达敌人生成期望速度，再由局部避让选择实际速度
- 进入有效攻击距离后停止。当前距离已经被某条打得到这个目标的模式盖住，就停
- 前线阻塞时先尝试改锁一个直线可达的附近敌人，再沿人少的一侧侧移；不包含战术包抄、绕后或编队命令
- 椭圆碰撞约束负责分离、推挤和重叠修正；禁止异常弹飞
- 长时间无进展、目标死亡或绕行失效时重新选择目标
- 攻击许可只由有效目标和合法射程决定，不因附近敌人数量或额外碰撞距离倍率而拒绝攻击；站位约束由移动和碰撞模块负责。
- 二维核心按简化 RTS 维护，不以保留一维胜率为目标；核实为旧补偿规则的限制应删除，不能新增无数据依据的兵种平衡倍率或命中人数上限。

开发实现与验收：
- 战斗 tick 不再把别的士兵当作硬障碍做 A*，也不调用 `search_detour()`；该函数保留给几何测试、直接调用和诊断。平坦地形上的局部避让由 ORCA 半平面完成。
- 所有存活单位先计算期望速度和参与状态，再统一解速度、统一积分；零速度单位不参与半平面。
- ORCA 邻居查询半径为 `(自身速度 + max_known_speed) * avoidance_horizon`，只保留最近的 `orca_max_neighbors` 个邻居。双方都参与时避让责任各一半；对方停止、未参与或这一 tick 期望速度为零时，移动方承担全部责任。
- 已经重叠时使用一个 tick 的推开时间；尚未重叠且对方不参与时，时间窗取 `min(avoidance_horizon, 到达停步时间)`。场地四边是硬半平面，不通过三维退路放宽。
- 无解时使用 ORCA 的最小违反退路；无进展窗口已满且解出的速度不足最大速度 20% 时，再尝试期望方向的左右 90° 和反方向，取沿期望方向投影最大的可行解。
- 非圆单位不直接套用圆盘半平面：期望速度的真实椭圆扫掠畅通时不加约束；不畅通时用外接半径加一条半平面，解出的速度还必须通过真实椭圆扫掠。仍不通过时依次测试反向、约 ±143°、±90° 和降速候选，最后才停步。
- 几何一致性：局部避让、实际移动和碰撞解算共用椭圆扫掠判定，整段平移不得穿过障碍。外接圆只用于快速排除，不把圆重叠直接当成椭圆路径堵塞。
- 移动和朝向共同组成 `PoseMotion` 动作，转向与平移可以同时发生，不再要求先原地完整转向。求解器输出速度、最终占位朝向和转向占本 tick 的比例，执行层不得另选轴向或切线运动替代它。
- 所有单位共用期望速度、改目标、侧移、ORCA 和碰撞解算流程；形状差异只决定半平面与真实扫掠是否可用，不决定某个单位是否拥有脱困动作。
- 椭圆占位正常逐步转向，所有候选动作检查完整位姿扫掠，不能仅凭起点和终点不重叠就放行。默认占位转向上限为每秒 2π 弧度，是本模型运动求解参数，不宣称读取了原版转向数据；它不改变攻击抬手或射速。圆的旋转不改变占位，可以省去对应几何计算。
- 执行层分子步重验同一动作；若其他单位已进入路线，只执行该动作已验证安全的前缀并停下本 tick 剩余运动，不再偷偷改写速度方向或下一子步追回未走的距离。被动挤动不自动改变占位朝向，也不打断攻击准备。
- 接敌和到达停步参与时间窗计算：到攻击位置后不假定继续沿原方向冲进目标，真正无解时允许停下，不用穿透换取“始终在动”。
- 编队间距按出生朝向的两轴投影计算；边界限制按椭圆在世界 X/Y 上的实际投影计算，不以最大半径四面扩宽。攻击、搜索距离及 AOE 语义不随本次几何整理改变。
- 椭圆扫掠沿用有界支撑轴搜索，移动转向区间采用保守包围并按需细分；圆形保留解析快路径。
- 使用历史最佳距离和短时位移窗口检测停滞、振荡；单次往返不能清零全部进展记录。
- 目标死亡、暂时无法直线接敌或侧移失效时重新选择目标；所有替代目标都被挡住时保留脱困计数，不通过不断换目标清零恢复过程。
- `scripts/aoe3_pathing_audit.py` 可读取查看器历史或复跑固定国战阵容，统计振荡片段、低速滞留、异常长路线和重叠；应同时比较这些指标，不能仅用零重叠或少反向次数验收。运行日志中的 `2d-motion` 记录异常单位和 tick。

### 3.5 攻击判定

#### 攻击模式选择

单位带攻击列表时，对当前目标按下面五步选一条。一条模式是一整包：伤害、伤害类型、射程、攻速、溅射、弹丸、抬手、倍率。伤害类型只决定吃哪种护甲。

1. 已打开、伤害大于 0、射程盖住当前距离，才进候选。蓄力还要条是满的，而且冷却大于 0。冷却缺省或小于等于 0 的蓄力留在列表里，不自动打出。开局蓄力条是满的，这是模拟默认，不是 XML 字段。
2. `<rate type>` 对不上当前目标的不进候选。没写目标类型的攻击打谁都行。`Unit`、`All`、`Military` 打得到普通单位。
3. 候选里取优先级最高的一条。优先级是这份阵型给该动作写的 `priority`，没写就是 0。同优先级再比最大射程，再比动作名。
4. 已经有一条盖住当前距离，就站住，不为了优先级更高、但更近的那条继续靠近。已经站在更近的射程里才用那一条，不后退。
5. 落在两段射程中间，向更近的那条走进去。已经贴进最小射程里面，不后退。

搜敌半径只用打得中人、并且现在打得出来的最远射程。打建筑、打船、打守护者、砸箱子的更远射程不把搜索圈撑大。

#### 纯远程与最小射程

- 当前能打中这个目标的模式都有最小射程时，不走进最小射程里面硬打。
- 最小射程为 0 的模式可以贴脸打，不减伤。
- 不凭空生成半伤射击，也不额外赋予自动后撤。

#### 已删除的贴脸补偿

旧模型允许纯远程在最小射程内打 50% 伤害，这是无原作数据依据的补偿。
2026-09-23 从二维引擎删除。有攻击列表时不再另做贴脸折扣。

#### 攻击抬手（Windup）

**2026-09-23 用户确认的简化规则**：抬手表示进入攻击准备姿态，不是只针对某个目标的一次性瞄准。站定后保持“瞄准、连续攻击”状态；主动行动视作离开这一姿态，但不代表武器冷却完成。不读取完整动画，不模拟飞行物，也不额外添加后摇移动锁。

抬手和 ROF 使用两个独立的绝对到期时刻：

```text
aim_ready_at    = 本次开始准备的时间 + 对应攻击方式的 windup
attack_ready_at = 上次实际出手时间 + 那次攻击的 ROF

可以出手 = 现在 >= 两个到期时刻
          且保持停步攻击状态
          且目标存活、敌我关系正确、所准备攻击方式仍在合法射程内
```

两个时间并行推进，移动后再攻击的等待时间仍等于 `max(剩余 ROF, 新抬手时间)`，不是相加。时间以模拟 tick 为准，重复处理同一 tick 不会多扣时间或多打一发。

| 情况 | 攻击准备 | ROF |
|---|---|---|
| 首次停下接敌 | 按选中的那条模式开始完整抬手 | 独立检查是否就绪 |
| 原地同方式持续攻击 | 保持已完成的准备，不额外叠加 windup | 每次实际出手后设置新的到期时刻 |
| 原地同方式转火 | 保留已有进度；没完成的抬手不会瞬间完成 | 不重置、不延长 |
| 目标死亡或暂时没有合法目标，尚未主动移动 | 清除无效目标，但保留准备姿态和计时 | 继续推进 |
| 主动移动，包括发出了移动意图但被挡住 | 取消准备；再次停下后重新抬手 | 继续推进，不清空或重新计时 |
| 被动挤动、碰撞修正或小幅转向 | 不取消准备 | 不变 |
| 当前这条模式失效，必须换另一条 | 用新的一条重新抬手 | 保留原冷却，到下一次真正出手才使用新一条的攻速 |

`prepared_mode` 锁定本次准备的攻击方式。抬手完成但仍在等 ROF 时也保持该方式，只要仍合法，不因距离微抖反复切换。一击完成后允许为下一轮重新选择方式；同方式继续不重新抬手，实际换方式才重新准备。

例如抬手 0.4 秒、ROF 1.5 秒：第一次从 0 秒开始准备，则在 0.4 秒出手；保持同一攻击方式时后续为 1.9 秒、3.4 秒。若另一次在 0.8 秒重新停下，抬手到期为 1.2 秒，而原 ROF 到期为 2.0 秒，则最早在 2.0 秒出手。

**数据边界**：抬手和攻速用选中那条模式自己的数值，缺失时为 0。不提取完整动画时长。实际伤害在出手 tick 立即结算，没有飞行时间。

**开发查看器**：兼容字段 `attack_cd` 仅表示 ROF 剩余秒数；新增 `aim_cd` 表示抬手剩余秒数（`null` 为未准备），`prepared_mode` 表示所准备的攻击方式。它们由到期时刻推导，不再用一个可变倒计时混合两种含义。

查看器帧还额外导出 `prepared_action_name`（当前准备的动作名）、`charge`（最主要的蓄力动作的 `ready / remaining / recharge / ratio`）与 `unit_templates`（按兵种去重的攻击模式清单，含伤害、伤害类型、射程、攻速、优先级、是否蓄力与冷却）。攻击视觉事件带 `action_name / action_charge / action_damage_type`，用于区分普通攻击与蓄力出手。

##### 历史调研与当前取舍

以下保留历史调研作为精度边界；当前以用户确认的轻量模拟规则为准，不自动扩展为完整动画或弹道工程。

**问题 1：windup 数值可能不精确**

当前 parser 直接将 anim XML 的 `<tag type="Attack">` 值当作秒数。但 Steam modding 指南
（[Proto & Anim Action & Logic Lists](https://steamcommunity.com/sharedfiles/filedetails/?id=821258879)）
明确写道 tag 值是**动画运行时间的百分比位置**（0.0~1.0），Fandom Wiki Attack Delay 词条也在
Bang Engine 章节确认 *"attack delays are handled with animation completion percentages in tandem
with tags"*。正确公式应为 `windup_seconds = tag_fraction × GrannyAnim固有时长`，需从 .gr2
二进制文件提取动画时长。

但 ESOC 社区和 Fandom Wiki 各单位页面又都直接把 tag 值报成秒数（如长弓 0.98s、散兵 0.46s），
可能是多数攻击动画时长接近 1 秒所以误差不大。有资深玩家提供的数据（长弓 1.47s、弩手 0.35s）
与 tag × 动画时长模型吻合，但未能用第三个单位做决定性验证。

历史备选方案是读取 .gr2 动画时长后换算（参考 [AOE3GR2Exporter](https://github.com/zzqqqzzz/AOE3GR2Exporter)）。用户已明确当前不做这项工作，沿用现有近似参数。

**转火语义：已确认为保留准备姿态**

原作自动转火的具体动画中断机制未完全核实。本项目已经明确采用“未主动移动且攻击方式不变，原地转火保留准备进度”的简化规则。这不再是待补上完整抬手惩罚的缺陷，也不能因旧资料存在不确定性而擅自改变这一决定。

#### ROF（攻击间隔）

- ROF 用这一下选中的模式自己的攻速
  - **攻速单位是秒（攻击间隔）**，不是攻击频率。`3.0` 表示每 3 秒攻击一次
- 攻击当帧结算（不模拟弹道飞行时间），伤害立即生效

#### 缺失 ROF 的处理

- 远程 ROF 缺失 → 默认 3.0 秒
- 近战 ROF 缺失 → 默认 1.5 秒

#### 不实现的机制（明确排除）

为保持模拟简洁，**以下机制不予实现**：
- ❌ miss / 闪避率
- ❌ 距离衰减曲线（射程内伤害随距离递减）
- ❌ 装填中断 / 重新瞄准时间
- ❌ 弹道飞行时间
- ❌ 散射 / 抛物线落点
- ❌ 兵种在另一份阵型里才有的攻击。玩家不在齐射、交错、防御、掩护之间切换。骑兵碾压在 `Trample` 阵型里，出生阵型没有，不打
- ❌ 建筑上的蓄力射击
- ❌ `hitpercent`、`stunduration`、`accuracy`、`CanDodgeAttacks`
- ❌ 葡萄弹关掉架炮之后的进场变化。架炮前不能开火、架好才打，照旧

### 3.6 目标选择

- 士兵**停止移动后立即锁定目标**（不是预先锁定）
- **锁定优先级：射程内最近的存活敌方个体**
  - 射程内只有一个敌方 → 直接锁定
  - 射程内有多个敌方且**距离不同** → 锁定**最近**的
  - 射程内有多个敌方且**距离相同**（如同兵种重叠） → **随机**选一个锁定
- **锁定目标直到其死亡**，当次攻击伤害溢出不转火
- 目标死亡后**下一个 tick 重新按上述优先级锁定新目标**（看射程内谁最近，距离相同才随机）
- **攻击阶段不重新锁定**：目标锁定在每 tick 攻击之前统一完成，开火阶段中即使目标被别人打死也不会临时换目标（打尸体 = 火力浪费）

> **设计意图：排布阵型 + F2A 对冲 + 火力浪费**  
> 双方按排列展开（近战前排、远程后排），"最近优先"锁敌自然集火前排。  
> 前排死光后，下一排距离最近被锁——逐排清扫，避免火力分散零伤亡。  
> 攻击阶段不换目标保证了真实的火力浪费：多门炮锁同一个兵，第一门杀了它，其余全是打尸体。  
> 参数可调：`ROW_CAPACITY`（每排人数）、`ROW_SPACING`（排间距）、`FORMATION_MAX_DEPTH`（最大纵深）。
### 3.7 伤害计算

#### 公式

```
伤害 = 基础攻击力 × 倍率乘积 × (1 - 目标对应抗性)
伤害最低为 1
```

#### 三种伤害类型与三种抗性的对应关系

AOE3 有三种伤害类型，每种只被对应的抗性减免：

| 伤害类型 | 对应抗性 | 数据字段 |
|---------|---------|---------|
| 远程伤害 (Ranged) | 远程抗性 | `armor_ranged` |
| 近战伤害 (Hand/Melee) | 近战抗性 | `armor_melee` |
| 攻城伤害 (Siege) | 攻城抗性 | `armor_siege`（极少见，数据中暂无） |

**关键含义**：
- 鹰炮的攻城攻击打步兵 → 步兵通常没有攻城抗性 → 0%减免 → 全额伤害
- 这就是为什么炮兵打无甲单位特别疼
- 绝大多数兵种只有近战抗性或远程抗性（或两者之一），极少有攻城抗性
- 数据中同时有双抗的兵种只有 5 个（如阿扎普、利菲迪骑士等）

#### 伤害类型

这一下的伤害类型是选中那条模式自己的 `damagetype`，只决定吃哪种护甲，不决定它算远程还是近战。

- `Ranged` 吃 `armor_ranged`
- `Hand` 吃 `armor_melee`
- `Siege` 吃 `armor_siege`（极少有单位写了这个抗性）

鹰炮主炮的伤害类型是攻城。它打没有攻城抗性的步兵时不减免。

#### 倍率计算

- 目标可能同时属于多个类型（如 [Cavalry, Shock infantry]）
- 攻击者的倍率列表中，所有匹配目标类型的**倍率叠乘**
- 例：攻击者对 Cavalry ×0.5、对 Shock infantry ×2.0 → 最终倍率 = 0.5 × 2.0 = 1.0
- 无匹配倍率时 → 倍率 = 1.0

### 3.8 AOE（范围伤害）

#### 数值精度与运算规范（2026-09-30）

**展示层**

- 所有玩家可见的战斗数值（HP、攻击、速度、射程、AOE、倍率等）按整数显示。
- 展示取整不反向写入 `Unit` 或 seed。

**内部运算**

- `Unit` 内部使用浮点值，不使用 `Decimal`；小数位数不增加运算复杂度。
- 基础数据本来就有小数的字段必须完整保留，不能在解析阶段提前取整。
- `hp` / `train_time` 最多保留 1 位；`damage` / `maxrange` / `minrange` / `damagearea` / `damagecap` 保留 2 位；`rof` 保留 3 位。
- `damagebonus` / 倍率属于高影响字段，保留 4 位。
- AOE 半径是特例，必须保留小数，不能用 `round()` 变成整数。

**性能**

- 小数精度本身不改变单次运算复杂度；性能影响主要来自几何计算，不来自保留 1 位还是 4 位。
- 当前 AOE 占位边缘距相对中心距的微基准约为 `1.25x`，单目标约增加 `0.044µs`，在斗蛐蛐规模内可忽略。

#### 设计原则

- **不考虑兵种的特殊攻击模式**（如炮兵霰弹模式、骑兵践踏模式等），每个兵种只使用其默认/主攻击模式
- 场地使用二维空间，AOE 按二维欧氏距离筛选候选目标

#### 数据来源

- 直接从游戏文件 `protoy.xml` 的 `<protoaction>` → `<damagearea>` 字段解析（`scripts/crawler/aoe3_gamedata_parser.py`）
- 当前 `units.json` 中 **147 个单位**带 AOE 数据（重型加农炮 / 迈索尔火箭炮 aoe=4，胸甲骑兵 melee aoe=2，战舰类 aoe=1 等）
- 每个攻击模式的 AOE 与该模式的 damage / range / multipliers 整体绑定，不存在拼接

#### AOE3 原版溅射机制（解包 + 社区实测，引擎逻辑不在 XML 里）

**解包可见字段**（`protoy.xml` → `<protoaction>`，与代表攻击整包绑定）：

| 字段 | 含义 |
|------|------|
| `<damagearea>` | 溅射半径（游戏内 AoE 圆半径） |
| `<damagecap>` | **溅射总伤害池**（不含主目标全额伤害；主目标另算） |
| `<basedamagecap>` | 多为 `1`，表示伤害上限随科技/升级按 BasePercent 缩放（见 `techtreey.xml` 的 `subtype="DamageCap"`） |
| `.tactics` `<areasortmode>` | `Radial` / `Directional`，决定 AOE 是全圆还是方向性区域 |
| `.tactics` `<outerdamageareadistance>` | 距离衰减的外圈距离参数 |
| `.tactics` `<outerdamageareafactor>` | 外圈最低伤害系数 |

对应 seed 字段：

| tactics / protoy | units.json |
|---|---|
| `areasortmode` | `area_sort_mode_ranged/melee` |
| `outerdamageareadistance` | `outer_damage_area_distance_ranged/melee` |
| `outerdamageareafactor` | `outer_damage_area_factor_ranged/melee` |
| `basedamagecap` | `basedamagecap_ranged/melee` |

**解包里没有**溅射分配公式（距离衰减、随机选目标、Bolos 弹跳等特殊模式均在引擎 C++ 里）。社区/实测共识（AoE3 Heaven、ESOCommunity、Fandom）：

- 主目标：完整单次伤害（含弹丸合并），**不计入** DamageCap 池
- 溅射：以主目标为圆心、`damagearea` 为半径；**DamageCap 限制的是溅射能造成的总伤害**
- 多数单位 `damagecap ≈ 2×` 该动作的 `damage`，但**以 protoy 为准**（如迫击炮 `BarrageAttack`：damage 30、cap 90）
- 原版在范围内**按距离衰减**、目标选取也不完全是「均匀随机」；部分单位（如 Bolas）有独立弹跳逻辑

#### 斗蛐蛐简化 AOE 模型

二维场地中以真实位置判断溅射；2026-09-23 删除旧人数配额、随机抽取和
`DamageCap / 人数` 均分规则：

- 有 AOE 属性的兵种攻击时：
  - 主目标受 **100% 完整伤害**
  - 以主目标位置为命中点，排除主目标，按**占位边缘距**筛选半径内的敌方个体：
    - `AOE 距离 = 中心距 − 主目标沿连线方向的占位 − 副目标沿连线方向的占位`，最小为 0。
    - 两个单位身体相贴时距离为 0；椭圆占位按单位当前朝向计算连线方向上的厚度。
    - 距离衰减与 cap 排序使用同一个边缘距。
    - 2026-09-30 选定：中心距会让 `AOE=1` 几乎只能打到完全贴身的步兵，也让 `damagearea=0.25/0.5` 永远打不到人；边缘距同时吻合旧版铁连枷打并排骑兵、火箭炮贴身两人满伤、决定版小数半径数据。原版公式未公开，这是按实测对照选出的模型。
  - `damagearea` 保留原版小数，不取整。
  - `area_sort_mode` 来自 `.tactics`：
    - `Radial`：全圆筛选。
    - `Directional`：只保留攻击方向前方的目标。
  - 距离衰减按 `outer_damage_area_distance` / `outer_damage_area_factor`：
    - 无参数时，半径内系数为 1。
    - 有参数时，命中点处系数为 1，到外圈距离后降为外圈系数，并在半径内保持该下限。
  - **DamageCap**：优先使用本次攻击槽位的 `damage_cap_*`；没有正数 cap 时使用 `合并基础伤害 × 2`，即 `damage × num_projectiles × 2`。
  - 缺 cap 的两倍兜底是用户明确确认保留的模型决策，不得作为未授权平衡补丁删除，也不宣称这是原作引擎的已证实缺省值。
  - 副目标按到命中点的距离从近到远排序，依次消耗 cap：
    - 每个目标基础伤害 = `合并基础伤害 × 距离系数`。
    - 实际分配 = `min(基础伤害, 剩余 cap)`。
    - 最终伤害 = `实际分配 × 克制倍率 × (1 - 护甲)`。
    - cap 耗尽后，不再命中更远的副目标。
  - 主目标不消耗副目标 cap；超杀不转移。
  - 不随机选目标，不按人数均分，不把每个副目标的伤害上限写成 `cap / 人数`。
- `aoe_radius` 字段缺失或为 0 的兵种 → **单体攻击**，不走 AOE 流程
- 兵种实际有 AOE 但字段缺失 → **数据 bug**，列入 §四数据缺失清单修复
- 模拟器**不做兜底猜测**（不能“看到是炮就猜 aoe=3”，数据是什么就是什么）

### 3.9 攻击列表

**数据源**：游戏文件 `protoy.xml` 中每个 `<unit>` 的 `<protoaction>` 元素，
每个 protoaction 的 `damage / damagetype / maxrange / minrange / rof / damagearea / damagebonus*`
**整体绑定**——同一个 protoaction 的所有字段是一套真实游戏数据，铁律：**不可拆分拼接**。

#### 核心概念：攻击模式 vs 伤害类型（正交！）

这是两个**完全独立的维度**，**绝不能混淆**：

| 维度 | 取值 | 由谁决定 | 影响 |
|------|------|---------|------|
| **攻击模式（动作名）** | `HandAttack` / `RangedAttack` / `BuildingAttack` 等 | 引擎按动作名硬编码绑定行为 | 动画、弹道、是否停步、是否触发闪避 |
| **伤害类型** | `Ranged` / `Hand` / `Siege` | protoaction 的 `damagetype` 字段 | 吃哪种护甲（armor_ranged / armor_melee / armor_siege）|

**关键认知**：AoE3 引擎**不存在"远程/近战"的概念划分**。一个单位停在一份阵型里，引擎按动作名挑一条模式。

单位出生阵型里的攻击列表是唯一战斗口径：出手、进池、战力、国战角色、单位卡、配兵摘要、兵种对比、一行简介，以及打到列表上的科技，都读这份列表。2026-10-08 起，解析器不再写出远程、近战、攻城三个代表槽，`Unit` 也没有这些字段。

**举例**（伤害类型属于具体 protoaction，与该 protoaction 是远程还是近战无关）：

- ✅ **远程攻击 + Siege 伤害**：鹰炮主炮（`CannonAttack, damage_type=Siege`）
- ✅ **近战攻击 + Siege 伤害**：沙漠突袭者（`MeleeHandAttack, damage_type=Siege`）
- ✅ **远程攻击 + Hand 伤害**：战斧兵投斧、飞刀手（`RangedAttack, damage_type=Hand`）
- ✅ **近战攻击 + Hand 伤害**：绝大多数近战兵（默认情况）
- ✅ **全 Siege 多模式**：火兵有 10 种攻击模式全部 `damagetype=Siege`

> 因此 parser 的"槽位归类"和"伤害类型识别"是**两套独立判断**：
> - 归 melee/ranged 槽位 → 看**动作名标签**（引擎行为的唯一真实依据）
> - `damage_type_*` 字段 → 直接抄 protoaction 的 `damagetype`（决定它打哪种护甲）
>
> **绝对禁止**用 `damagetype` 来判断攻击归属哪个槽位。

**实现位置**：列表在 `scripts/crawler/aoe3_gamedata_parser.py` 写出，运行时读 `src/plugins/aoe3/attack_actions.py`。

#### 攻击列表

出生阵型决定列表收哪些动作。单位写了 `<initialtactic>` 就用它。没写时：带 `Limber` 又带 `Bombard` 用 `Bombard`，否则 `Volley`，否则 `Stagger`，否则 `Melee`，否则用第一份不在 `Limber`、`Stealth`、`Cover`、`Defend` 里的阵型。船的阵型文件用 `Normal`、`Line`、`Wedge`，没有 `Volley` 时落到 `Normal`。

只收这份阵型里的动作，再按下面去掉：

- `type` 不是 `Attack`，并且没有 `attackaction=1`，不收。治疗、自动采集、施法因此不进。四辆彩蛋卡车的 `TruckAttack` 标了 `attackaction=1`，收。
- 阵型里有这个动作，单位自己的 proto 包没有同名伤害，或伤害小于等于 0，不收。不拿阵型文件里的伤害来补。
- `InflictsNoDamage` 的单位列表是空的。
- **按动作名排除英雄技 / 一次性技能 / 召唤类**：黑名单 `NON_DPS_RANGED_ATTACKS`，定义在 `scripts/crawler/aoe3_gamedata_parser.py`，当前含 `SharpshooterAttack`（狙击手攻击）、`CrackshotAttack`（神枪手攻击）、`SwashbucklerAttack`（扫荡攻击）、`HeavenlyFireBomb`（天火）、`Stun`（击昏）、`Chaos`（混沌）。原因见下。
- 除上面这条黑名单外，不按动作名整类删。没有标成蓄力的 `Charge` 就是普通攻击。骑兵碾压在另一份 `Trample` 阵型里，出生阵型范围已经把它留在外面。
- 不按目标类型预先删。`<rate type>` 对不上当前目标时，出手那一步不用它。`All` 打得到人。
- 单位 proto 包写了 `<active>`、`<chargeaction>`、`<auxchargeaction>` 时，以单位自己的为准，盖过共用阵型文件。没写就用阵型文件的。`active=0` 留在列表里，标成关着，直到一份真正打到这个单位的科技把它打开。

共享阵型文件是模板。同名 proto 包只在写出上述开关时覆盖。

**为什么保留这份黑名单**：这 6 个是被排除单位手动释放的主动技，不进全自动斗蛐蛐的常态输出循环。原始数据里没有能按动作读取的冷却：单位级 `<rechargetime>` / `<auxrechargetime>` 只在动作标了 `chargeaction` / `auxchargeaction` 时才写进 `recharge`，而这 6 个动作在 `data/aoe3/raw/tactics/*.tactics` 里一个都没有标蓄力。所以它们没有可用的冷却门，一旦进列表就会被当成普攻循环。实测去掉黑名单后的危害：`SwashbucklerAttack`（36~150 伤害、射程 2）和 `Stun`（30 伤害、射程 14）能通过其余全部筛选真的开火，17 个单位 × 8 个常见兵种的 136 场里 34 场结果改变、9 场直接翻盘。`SharpshooterAttack`、`CrackshotAttack`、`HeavenlyFireBomb`、`Chaos` 靠 `rate` / `hits_soldiers` / `active` 本来也基本打不到普通兵，但仍一并列出，避免以后数据变动时漏网。新增同类英雄技时，把动作名追加进这个集合。

打得中人：类型不是 `Attack` 且没有 `attackaction=1` 的不算。目标类型里带 `Guardian`、`Building`、`Ship`、`Crate`，或正好是 `Herdable`、`Tree`、`Huntable`、`Resource`、`Fish`、`BerryBush` 的不算。没写目标类型、类型是 `Attack` 的算。`Unit`、`All`、`Military` 算。

#### 展示

单位卡、配兵面板、兵种对比最多显示当前阵型里优先级最高的两条。同优先级保持阵型里的先后。标题是动作名。关着的也占这两条，标成关。拆建筑的如果排进前两名，照样显示。

单位卡和兵种对比写伤害、伤害类型、射程、攻速、前摇、溅射、弹丸、蓄力和倍率。配兵面板写动作名、伤害、伤害类型、射程、攻速，有溅射或关着才补。一行简介在没有现在开着、打得中人、伤害大于 0 的模式时不写攻击，否则用同样的前两条，写成动作名加伤害。

克制行和国战角色只看这些开着、打得中人、伤害大于 0 的模式自己的倍率。关着的蓄力和只拆建筑的不算。标签门槛不变。纯治疗看这些模式里的最大伤害。

#### 运行时科技

一份科技先换 `InitialTactic`，再处理同一份科技里的 `ActionEnable`。预备军的 XML 顺序相反，必须先换阵型，否则枪从关着的齐射重建出来，仍然关着。

一份科技里的每一条效果都带自己的作用对象（`ProtoUnit` 目标），只打写明的兵：兵种 id 不分大小写相等，或兵种标签相等。整条科技命中的兵种名单只决定这条科技能不能选，不决定一个兵吃到哪些效果。没写兵种的效果不打任何兵。

`InitialTactic` 把该阵型的动作整份换成当前列表。`ActionEnable` 和 `RechargeTime` 按动作名打到当前列表。伤害、射程、溅射、攻速、倍率也按动作名打到当前列表：写了攻击名只改那一条，写 `allactions` 或没写攻击名改全部；同一条上，点名和 `allactions` 按统一算符**相加**，不取大。伤害倍率同时改伤害和溅射池。「所有近战攻击伤害」（`DamageForAllHandLogicActions`）只改阵型里标了近战逻辑（`handlogic`）的攻击。

护甲效果按写明的伤害类型改对应护甲：近战（`Hand`）→ 近战护甲，远程（`Ranged`）→ 远程护甲，攻城（`Siege`）→ 攻城护甲。

结算不了的效果不静默丢弃：`civ_war_techs.UNAPPLIED_EFFECTS` 按「效果种类 × 算法 × 护甲类型」列明，科技池里出现未列明的效果时测试失败。

配兵摘要按兵种写各自吃到的效果；不同兵吃到的效果不同时分组写，如「攻城箭术：【长弓兵】开启攻击：远程建筑攻击…；【游骑兵】生命+15%…」。打不到这个兵任何攻击的效果不写。 可选科技同口径：只有对这个兵真正落地的效果才算命中（攻击类效果要求它有那种攻击），写明打到它但什么都不改的科技不可选。

只应用已经在生效名单里的科技。不按文明名自动补一份出生科技。

**设计原则**：
- **type / multipliers.vs 直接存游戏原始标签**（`AbstractCavalry`、`AbstractHeavyInfantry` 等），不翻译
- **倍率天然匹配**：`damagebonus.type` 和 `unit.type` 来自同一份 XML 同一套字符串，倍率匹配 = 字符串相等比对，不需要映射表
- **翻译只在展示层**：`i18n_zh.json` 负责 `AbstractXxx → 中文`，与数据/匹配逻辑解耦

#### 写入 units.json 的字段

每个动作名各自一整包写入 `attack_actions`：伤害、伤害类型、最小/最大射程、攻速、溅射半径、
溅射池、弹丸数、抬手、倍率、优先级、开关、是否蓄力与冷却。同一动作名的这些值一起从
protoy 伤害包 + tactics 定义取出，不跨动作拼装。每个阵型各存一份（`attack_actions_by_tactic`）。

> **damage_cap**：有 proto `damagecap` 时**必须用该值**；有溅射半径但动作没有正数
> `damage_cap` 时，按用户确认的口径兜底为 `合并基础攻 × 2`。禁止砍掉 AOE 当作「无 cap」处理。

> 2026-10-08 起不再写远程、近战、攻城三个代表槽。`Unit` 没有这些字段，出手只读
> `attack_actions`。下列早先关于槽字段的段落是历史记录，保留供对照，不再是现行规则。

#### 战斗池准入

`has_attack`：`InflictsNoDamage` 为假，且攻击列表里至少一条打得中人、伤害大于 0、射程大于 0。只拆建筑、打不到人的为假。

木制牛的拆建筑攻击目标类型是 `All`，打得到人，`has_attack` 为真。它不进普通池，是因为写在 `BATTLE_BLACKLIST` 里，攻击数据不改。

列表写空的单位，修法是补 protoy 伤害包或该动作的初始阵型，不要给 `has_attack` 加白名单。

#### 模拟器读哪一份

- 这一下的伤害、伤害类型、射程、攻速、溅射、抬手、倍率都用选中的那条。溅射和伤害必须来自同一条。
- 回放里的近战、远程标签仍用伤害类型是 `Hand` 且最大射程小于 6，不是阵型里的 handlogic。

#### 示例

| 兵种 | 写入 units.json 的 attack_actions |
|------|-------------------------------------|
| 鹰炮 falconet | `CannonAttack`（80 伤, 射程 0–26, 攻城, AOE 4）、`BombardAttack`、`CaseShotAttack`（关着） |
| 火枪手 musketeer | `VolleyRangedAttack`（23 伤, 射程 2–12）、`BuildingAttack`、`VolleyHandAttack`（13 伤, 近战） |
| 胸甲骑兵 cuirassier | 近战主攻击一条（35 伤, 近战, AOE 2） |
| 缴获臼炮 captured_mortar | 只有拆建筑动作，`has_attack` 为假，进不了池 |

### 3.10 单位改良（科技加成）

> **Status**: ✅ 已实现（2026-05-29）。数据源 `data/aoe3/raw/techtreey.xml` → 离线生成 `seeds/aoe3/unit_upgrades.json`；运行时由 `src/plugins/aoe3/upgrades.py` 的 `apply_upgrades()` 按时代叠加。

#### 3.10.1 档位是「累加」不是「替代」也不是「连乘」

精锐 / 禁卫 / 帝王是**前置链**（帝王 `prereq` 要求已研禁卫，禁卫要求已研精锐），所以升到高档时低档**同时生效**。它们的 effect 多为 `relativity="BasePercent"`——**每档按「基础值」算增量，增量相加**：

```
升到帝王火枪 = 基础 × (1 + 0.20 + 0.30 + 0.50) = 基础 × 2.00 = 200%
```

不是替代（×1.5），也不是连乘（×2.34）。火枪兵示例（基础 HP150 / 远程23 / 近战13）：

| 档位 | 系数 | HP | 远程攻 | 近战攻 |
|------|------|-----|--------|--------|
| 无 | ×1.00 | 150 | 23 | 13 |
| 精锐 Veteran | ×1.20 | 180 | 27.6 | 15.6 |
| 禁卫 Guard | ×1.50 | 225 | 34.5 | 19.5 |
| 帝王 Imperial | ×2.00 | 300 | 46 | 26 |

> 「指定某档」= 把该兵种**从无到该档的所有**逐时代升级（可研究 `UpgradeTech` + 通用 `Shadow` 自动档，见 3.10.5）增量按下表规则合进去，**不是只取一条**。

**各类别血/攻累加曲线**（实测自 `techtreey.xml`，含 `Shadow` 自动档）：

| 类别 | 2时代 | 3时代 | 4时代 | 5时代 | 说明 |
|------|-------|-------|-------|-------|------|
| 标准步/骑 | 100 | 120 | 150 | 200 | 精锐/近卫/帝王（可研究） |
| 散兵 | 100 | 120 | 150 | 200 | 精锐为 `Shadow` 自动档，余同标准 |
| 炮兵 | 100 | 100 | 125 | 175 | 无精锐/近卫；age4 `FieldGun`+25、age5 `Imperial*`+50 |
| 土著战士 | 100 | 120 | 150 | 200 | age3/4 绑文明逐兵链，age5 议会 `ImpLegendaryNatives`+50 |
| 亡命徒 | 100 | 120 | 150 | 200 | 酒馆精锐 + `Shadow` 近卫/帝王（见 3.10.4） |
| 佣兵 | 100 | 100 | 100 | 150 | 全程无逐时代档，仅升帝王政客 +50 |

#### 3.10.2 范围：按 relativity 决定数学，按 subtype 映射字段

扫描 525 个 `UpgradeTech` 的 effect 分布后，**做不做取决于 `relativity`**（它决定怎么算），能干净映射到现有 `Unit` 字段的都做；解锁 / 经济 / 美术不做。

| subtype | 映射字段 | relativity | 累加规则 | 做 |
|---------|----------|-----------|----------|----|
| `Damage` | `attack_*`（带 `action=`，按动作名归槽） | BasePercent | 增量相加 | ✅ |
| `Hitpoints`/`HitPoints` | `hp` | BasePercent | 增量相加 | ✅ |
| `MaximumRange` | `range`（带 `action=`） | Absolute | 固定值相加（如 +2） | ✅ |
| `DamageBonus` | `multipliers`（缩放该兵**已有**克制倍率，非加新条目） | 主要 Absolute | 每条**正倍率(≥1)** += amount；惩罚项(<1)不动 | ✅ |
| `DamageArea` | `aoe_radius_*`（带 `action=`） | Absolute | 固定值相加 | ✅ |
| `RateOfFire` | `rof_*` | **Assign** | **覆盖（不累加）** | ✅ 语义不同 |
| `MaximumVelocity` | `speed` | 混合(Absolute/BasePercent/Assign) | Abs 加 / BP 乘 / Assign 覆盖 | ✅ |
| `ArmorSpecific` | `armor_*` | Absolute | 固定值相加 | ✅ |
| `Cost`/`TrainPoints`/`BuildPoints`/`WorkRate`/`ResearchPoints` | 经济 | — | — | ❌ 无意义 |
| `UpdateVisual` | 换模型 | Absolute | — | ❌ 纯美术 |
| `Enable`/`FreeHomeCityUnit`/`Lifespan` | 解锁 | — | — | ❌ 时代档不收 |
| `ActionEnable` | 打开某一条攻击 | — | — | ❌ 不写进时代档。已经打到单位身上的科技会按动作名打开，见 §3.9 |

**relativity → 累加规则**（引擎核心，约一张表）：

- `BasePercent` → 各档增量**相加**（Damage / HP / Velocity）；
- `Absolute` → 固定值**相加**（Range +2、AOE、Armor、DamageBonus 正倍率）；
- `Assign` / `Override` → **覆盖**，多档时最后一档生效，**不累加**（ROF、Cost）；
- `Percent`（仅 3 例）→ 乘当前值（多档时连乘）。

> **`DamageBonus`**：`subtype="DamageBonus"`，`unittype` 是被克制的类型，`amount` 是加上的数。只对已有的正倍率（>1）相加，不新建条目，不改小于 1 的惩罚。按动作名打到列表里的每一条，见 §3.10.3。

##### 落地方式：时代升级 = 科技 id 列表 + 统一结算（2026-10-09 起）

生成器 `aoe3_upgrades_parser.py` / `aoe3_civ_upgrades_parser.py` 只记录每个兵、每个时代**已生效的科技 id**（累计），不预合并倍率。运行时 `apply_upgrades(unit, age, civ_id=None, tech_ids=())` 把这些科技、调用方给的科技（国战/配兵选中的），以及它们解锁的科技（`TechStatus active`、前置全部满足且原始状态为可获得的影子科技；`obtainable` 开放研究/造兵不生效，见 `src/plugins/aoe3/tech_links.py`）合并去重，再用 `src/plugins/aoe3/tech_effects.py` 一次结算：

- **同一个科技只生效一次；不同科技全部叠加，没有取大。**
- 统一算符（所有同类数据一致）：`BasePercent` 按基础值、各项增量相加；`Percent` 按当前值累乘；`Absolute` 相加；`Assign`/`Override` 覆盖。
- 每一项效果只打写明的兵（id 或标签），写了攻击名只改同名攻击；护甲按伤害类型，`Armor` 没写类型三种都加。
- 候选只收“到了时代就能拿到”的档：前置全是时代科技或同类升级档（`OrPrereqs` 任一即可）。只能由革命科技开放的档**不是时代升级**，直接排除。普通斗蛐蛐（无文明）只用通用线，通用线不使用文明专属档或前置要求文明专属科技的档；有文明时（国战、选国家的配兵）优先用该文明的独特科技，它经 `TechStatus active` 激活的通用档一并生效。
- 原始数据照算，没有脏数据名单：精锐投石索兵现为射程 +8（早期版本的 +147 已不存在）。
- **按动作名去重**：同一 effect 常对 Volley/Defend/Stagger/BuildingAttack 各出一条；每一条落到同名动作上，各记各的，不合并成一条，见 §3.10.3。
- 全量扫描：对所有有攻击单位 ×age{3,4,5} apply 后，**升级造成的越界 = 0**（基础数据自带的海军 x10/间谍 x40 等不在升级范围内，未被触碰）。

#### 3.10.3 与攻击数据铁律的关系（天生支持的原因）

`Damage` / `MaximumRange` / `DamageArea` / `DamageBonus` 都带 `action=`，按动作名作用。

时代升级与科技都按动作名结算：写了攻击名只改同名攻击（当前列表与各阵型副本各自按名匹配），`allactions` 或没写攻击名改全部。打到同一条攻击、同一个量上的多条效果按统一算符合并，点名与 `allactions` **相加，不取大**。伤害百分比同时改伤害和溅射池。

阿布枪帝王档：`VolleyRangedAttack`、`DefendRangedAttack`、`StaggerRangedAttack` 各 +4。`VolleyHandAttack` 不加。

#### 3.10.4 匹配方式：按 id 精确匹配（兵种升级）vs 按标签（全局，不做）

- **兵种升级**：effect 的 `<target type="ProtoUnit">Musketeer</target>` 与 `units.json` 的 **`id`**（= `internal_name.lower()`）精确匹配（`Musketeer`→`musketeer`）。验证：450 条 unit-only 改良覆盖 **268 个**有攻击的战斗单位；未匹配目标仅 16 个，全是非战斗对象（`Hero`/建筑/附着物），安全忽略。**这是精确名匹配，不是标签匹配。**
- **三大类「类别科技」（标签匹配，做）**：土著 / 亡命徒 / 佣兵在游戏里有**按大类**(非按兵)的战斗强化，标签匹配很干净（我们单位分别带 `AbstractNativeWarrior` / `AbstractOutlaw` / `Mercenary`，数量 native 系 / 53 outlaw / 66 merc），按时代给 +X% 血攻（`BasePercent` 累加）：

  | 大类 | 标签 | 代表科技 | 加成（血&攻） |
  |------|------|----------|----------------|
  | 土著 | `AbstractNativeWarrior` | `ImpLegendaryNatives`（age5，`UpgradeTech`） | **age5 +50%**；age3/4 的「绑定土著文明的按兵升级」由逐兵 id 链覆盖 |
  | 亡命徒 | `AbstractOutlaw` | 见下「亡命徒升级来源」 | **age3 +20% → age4 +30% → age5 +50%**（累加 100/120/150/200） |

  **亡命徒升级来源（为何「这么多」）**：亡命徒在**四种建筑**里训练，每种建筑各有一条 age3 精锐变体（同一档的多文明版本，一个文明只命中一条）；再叠一条**隐藏自动线**（`Shadow`）：

#### 3.10.5 选链规则：沿一条 prereq 链累加，优先通用线

同一兵种在同一时代常有**多条互斥升级变体**（通用线 vs 文明皇家卫队 RG vs 革命 Rev）。例：火枪兵 age4 有 `GuardMusketeers`（通用）+ `RGRedcoats`（英）+ `RGGuerreiros`（葡）。**禁止 age≤N 全加**（会把互斥变体一起叠、数值爆炸）。规则：

1. **逐时代独立选一条**：对每个时代 age∈{3,4,5}，在该兵种该时代的候选升级里**只选一条**，把其增量按 3.10.2 规则累加进选定时代之前的所有档。
2. **候选 = 可研究 `UpgradeTech` ∪ 通用 `Shadow` 自动档**（⚠️ 关键，曾漏）：部分兵种的精锐/近卫/帝王**不是可研究科技，而是 `Shadow` 隐藏档**（升到对应时代由引擎自动激活、UI 不显示），它们就是该兵的逐时代档，**必须纳入**。例：
   - 散兵精锐 = `VeteranSkirmishersShadow`（`prereq=Fortressize`，age3 +20%）→ 散兵实为标准 **100/120/150/200**（先前误算 180%，因只扫了 `UpgradeTech`）；
   - 亡命徒近卫/帝王 = `DEGuardOutlawShadow`(age4 +30)、`DEImperialOutlawShadow`(age5 +50)。
3. **必须按 prereq 解出该 `Shadow`/`UpgradeTech` 的时代并过滤文明专属**：只保留 prereq 为通用 `Fortressize`/`Industrialize`/`Imperialize` 的；**排除带文明前缀/无 age 前置的 `Shadow`**（`Age0<文明>`、`Imperialize<文明>`、`*AfricanShadow`、`Swedish*Shadow`、`DEAge0*`、`YPAA*StartingTechs` 等都是文明开局/专属加成，不进通用线）。同一兵同档若同时有可研究与通用 `Shadow`，二选一**不重复计**。
4. **优先通用线** `Veteran→Guard→Imperial`（含 `DEVeteran*`/`DEGuard*`/`DEImperial*` 及对应 `*Shadow` 等仅前缀/兵名/可见性不同的同构线）。
5. **回退文明变体**：若**某一时代没有通用线**，该档取文明变体 RG（例：长矛骑兵 `lancer` age4 用通用 `GuardLancers`、age5 无通用 → 回退 `ImperialGarrochistas`）。**逐档独立**，允许某兵 age4 通用 + age5 RG 混搭（无文明系统下的近似）。
6. **排除革命**（关键：革命本不该出现，是「搭便车」混入的）：tier 自动档靠 `Shadow` 标记识别（散兵精锐 = `VeteranSkirmishersShadow`，无研究按钮、必须认 `Shadow` 才捞得到），而**革命隐藏档也复用了 `Shadow` 标记**（`Rev*`/`DEREV*`/`DEHCREV*`），于是混进候选池——按前缀排除。同理开局 `Age0*`/`*StartingTechs`、文明专属 `*AfricanShadow` 等也是复用 `Shadow` 混入的噪音，一并排除。**「提纯 tier 线」= 认 `Shadow`/`UpgradeTech` 捞档 → prereq 解时代 → 排除革命/开局/文明专属/政客**，这是本功能脏数据处理的主体（`Shadow` 标记不纯所致）。
7. **2 时代 = 无军事改良**：普通战斗兵种的通用军改（含 `Shadow` 自动精锐）最早在 age3（`Fortressize`）解锁；age2 仅 1 条战役民兵改良，可忽略。**禁止 age≤N 把同档多条变体一起加**（否则通用+RG 叠加、数值爆炸）。

> ⚠️ **无文明系统的代价（记录给未来）**：英国红衣兵 `RGRedcoats` 等皇家卫队在游戏里强于通用禁卫，本方案按通用值算（略低）。**待将来加文明系统时**，可按对局文明选择对应 RG/革命变体链，替换通用线——届时选链规则的第 2/3 步改为「按 civ 选支」。

#### 3.10.6 指令、时代与展示

- **指令**：`斗蛐蛐 N时代`（N ∈ **2~5**）指定本局时代；可与现有模式/预算组合（如 `斗蛐蛐 火枪 散兵 5时代`）。**所有模式**都接受该参数（§④）。
- **对称**：双方**同档**（同一时代），两边一起缩放，LCM/王中王平衡基本不被破坏。
- **兵池按时代限定**：本局只抽 `unit.age ≤ N` 的兵（751 个战斗兵全有 `age`，0 缺失；Exploration1/Commerce2/Fortress3/Industrial4/Imperial5）。早登场单位（如瑞典皮革炮 age2、长弓 age2、廓尔喀 age2、age2 龙骑/弓骑）本就是**文明早登场特权**，照常出现。**不**因低时代兵变少而做特殊过滤规则。
- **默认**：不写时代参数 = **3 时代**（693 兵，含散兵/鹰炮等经典兵；通用军改从 age3 起，故默认就有改良）。
- **累计可用兵数**：age1=131 / ≤age2=516 / ≤age3=693 / ≤age4=755 / ≤age5=756。
- **预先结算**：开战前就把改良算进 `Unit` 副本（HP/攻/射程/AOE/倍率…），模拟器与兵种信息卡都用**加成后**数据；`_create_soldier` 不感知科技。
- **兵种信息卡**：直接显示**加成后**面板，**不逐条列**兵种独立升级（精锐/禁卫/帝王），避免冗余。
- **押注简报**：在简要对局信息里写明**本局时代**（如「⏳ 本局：帝国时代（5）」）。
- **类别科技展示**：在押注简报的时代之后，按本局是否含土著/亡命徒/佣兵单位，逐条列出已激活的类别加成（文本以 stringtable 实际译名为准）：

```
本局：帝国时代（5）
已激活类别科技：
  · 传奇土著战士：土著 血/攻 +50%
  · 雇佣兵契约：佣兵 血/攻 +50%
```

#### 3.10.6b 横向科技（普通对局不启用）

普通斗蛐蛐不再随机抽取兵工厂、教堂、主城卡或皇家卫队效果，也没有科技开关。
逐时代单位改良，以及土著、亡命徒、佣兵的类别科技仍按本节规则自动生效。

科技效果由 `src/plugins/aoe3/tech_effects.py` 统一应用；该模块不读取科技池、不随机选择科技，
只负责把未来国战明确选定的文明科技或主城国策作用到单位副本。

#### 3.10.7 实现分层（落地约定）

- **离线**（parser，无需游戏）：扫 `techtreey.xml` 生成 `seeds/aoe3/unit_upgrades.json`，按 id 索引、按时代给出**累计科技 id**，例如：

```json
{
  "musketeer": {
    "3": { "techs": ["VeteranMusketeers"], "name": "老练火枪兵" },
    "4": { "techs": ["VeteranMusketeers", "GuardMusketeers"], "name": "护卫火枪兵" },
    "5": { "techs": ["VeteranMusketeers", "GuardMusketeers", "ImperialMusketeers"], "name": "帝国火枪兵" }
  }
}
```

> 种子格式：`units[id][age] = {techs: [累计科技 id], name}`，`category[tag][age] = [累计科技 id]`；文明覆盖 `civ_unit_upgrades.json` 同格式。

- **类别科技**（土著/亡命徒/佣兵）按标签取该时代的科技 id，与逐兵线**一起叠加**。例：阿坎安科比亚 5 时代 = 精英 +25% + 风云 +35% + 传奇土著 +50% = ×2.1。早期“逐兵与类别取大”的规则是错误的，已于 2026-10-09 推翻。
- **运行时**：`apply_upgrades(unit, age, civ_id=None, tech_ids=())` 出副本（不改全局 seed），在进 `BattleSimulator2D` 前、阵容生成后应用；全部效果一次结算，见上文“落地方式”；兵种卡用副本渲染。
- **兵池过滤**：阵容生成入口按 `unit.age ≤ N` 过滤候选池（各 `get_*_pool` 加时代上限参数）。

## 六、独立测试模块（开发期工具）

为了便于在不卷入押注/经济/群消息的情况下专注调试战斗模拟器本体，需要一个**独立可运行的纯模拟测试入口**：

### 6.1 定位

- **不是**最终游戏的一部分，是开发期的**模拟器单元演练工具**
- 阉割掉押注、经济、群消息、状态机等一切非"模拟"内容
- 直接：`选两个兵种和数量 → 跑模拟 → 打印事件流和结果`

### 6.2 入口

- 脚本位置：`scripts/aoe3_battle_sim.py`（独立 CLI，与 `play_cli.py` 解耦）
- 调用方式：`uv run python scripts/aoe3_battle_sim.py`
- 提供三种运行方式：
  - **交互式**：菜单选兵种 → 输数量 → 跑

### 6.4 复用关系

- 测试模块直接 import 真实的 `simulator2d/` 核心引擎
- 即测试模块和正式游戏共用同一份模拟器代码，确保"测得过 = 跑得通"

## 七、调试日志规范（开发期强制要求）

> **背景**：电子斗蛐蛐是项目里规模最大、状态最复杂、最容易出 bug 的功能（二维移动与碰撞 + 个体 HP + 远近切换 + 抗性倍率 + AOE + 事件流分批播报，任一环出错都会"看起来跑了但结果不对"）。
> 因此 **要求开发期所有核心环节都必须打详细调试日志**，方便后续通过日志快速定位问题。

### 7.1 总体原则

- **宁多勿少**：开发期日志按"事无巨细"标准打，不要怕日志多
- **可开关**：通过日志级别（DEBUG / INFO / WARNING / ERROR）和命名 logger 控制输出
  - 默认 `DEBUG`：开发与独立测试器（§6）启用
  - 上线后调整为 `INFO`：群消息只看关键节点和异常
- **结构化优先**：日志内容包含关键字段（时间戳、单位 ID、坐标、HP、伤害值），便于 grep/正则筛选定位
- **可追溯**：每条日志带 tick 编号或模拟时间戳，能根据日志时间线还原战斗

### 7.2 必须打日志的关键环节

按战斗流水的发生顺序：

#### 阵容生成阶段
- `INFO` 兵种池筛选结果（数量、排除原因）
- `DEBUG` 每次随机抽兵种的候选与最终选择
- `INFO` 双方最终阵容（兵种、数量、总资源、人口、双方资源差异）
- `WARNING` 资源平衡多次重抽未达标时

#### 模拟器初始化
- `INFO` 战斗参数（场地长度、tick 间隔、最大时长）
- `DEBUG` 每个士兵的初始状态（id, 阵营, 兵种, HP, pos, 攻击力, ROF, 抗性）

#### 每 tick 主循环
- `DEBUG` tick 编号 + 模拟时间戳（每 tick 都打）
- `DEBUG` 移动事件：哪个兵种从 X 移到 Y，最近敌方距离
- `DEBUG` 攻击模式判定：`unit#A 距 unit#B = 4.2，选择=远程攻击`
- `DEBUG` 攻击执行：基础攻击、倍率链、抗性、最终伤害、实际攻击槽位
- `DEBUG` AOE 触发：主目标 + 溅射目标列表 + 各自伤害
- `INFO` 死亡事件：`unit#A (火枪手) 阵亡，剩余 X/Y`
- `DEBUG` 目标重新锁定：`unit#A 目标 unit#B 阵亡，重新锁定 unit#C`

#### 异常与边界
- `WARNING` ROF 缺失走默认值
- `WARNING` 伤害类型字段缺失走默认推断
- `WARNING` 模拟到达最大时长，按剩余 HP 比判胜
- `ERROR` 出现负 HP / 死亡单位仍被攻击 / 锁定不存在的目标 等不应出现的状态

#### 播报层
- `INFO` 每个 2 秒窗口的事件摘要（即使被跳过也要 DEBUG 记录"窗口跳过原因"）
- `INFO` 关键节点触发（开战 / 首杀 / 半灭线 / 终结）
- `DEBUG` 话术模板渲染前后的数据对比

### 7.3 实现约定

- 使用 Python 标准 `logging` 模块，**不要** `print`
- Logger 命名遵循模块层级：
  - `aoe3_battle.lineup`（阵容生成）
  - `aoe3_battle.simulator`（模拟器主循环）
  - `aoe3_battle.simulator.combat`（攻击/伤害判定）
  - `aoe3_battle.simulator.aoe`（AOE 计算）
  - `aoe3_battle.broadcaster`（播报层）
  - `aoe3_battle.economy`（押注与结算）
- 独立测试器（§6）默认输出 `DEBUG` 到 stderr，便于直接看
- 战斗模拟结束时，把完整事件流 dump 到一个临时文件（如 `/tmp/aoe3_battle_<期数>.log`），即使群里没看到日志也能事后翻

### 7.4 日志卫生

- 不要在日志里打巨型对象（如完整士兵列表的 repr），用关键字段
- 不要在循环最内层打超过 1 行的多行日志
- 上线时通过配置文件统一抬高级别，**不要**为上线临时删日志（删了下次还要补）

## 八、播报话术规范

### 8.1 总基调

- **朴素纪实 + 偶尔皮一下**——不堆形容词、不史诗渲染、不过度解说
- 让群友脑补，文字只提供"事实锚点"：兵种、数量、距离、伤亡数
- "皮一下"指偶尔吐槽真实数据带来的反常现象（鹰炮一炮 8 杀、雇佣兵打疯了），靠节制的吐槽自带笑点，不硬塞段子

### 8.2 播报片段格式（每 2 秒窗口）

#### 标准片段（窗口内有伤亡）

```
⏱ 04-06s
🔵 火枪手齐射，🔴 散兵 -2（剩 8/10）
🔴 散兵反击，🔵 火枪手 -1（剩 9/10）
📊 战况 🔴 8/10 vs 🔵 9/10
```

#### 极简片段（窗口零星击杀）

```
⏱ 14-16s
🔥 拉锯：🔴 -1 / 🔵 -1
📊 🔴 3/10 vs 🔵 4/10
```

#### 格式约定

- "📊 战况"行**每个非沉默片段都带**，给群友提供"打到哪了"的锚点
- 兵种动作词按"该窗口该方造成的死亡数"动态选词（§8.5）
- 每条播报后 sleep 2 秒，节奏接近真实战斗

### 8.3 关键节点（独立成条优先播报）

| 节点 | 触发条件 | 文案模板 |
|---|---|---|
| **开战** | 战斗开始 | 单兵种：`⚔️ 战斗打响！🔴 [10 火枪手] vs 🔵 [8 长枪兵]` 多兵种：`⚔️ 战斗打响！🔴 [2黑骑士 + 3祖瓦夫 + 11火枪手] vs 🔵 [1铁甲舰 + 7火枪手 + 16散兵]` |
| **首杀** | 整场第一次有人阵亡 | `🩸 第 X.Xs，🔵 长枪兵率先溅血，🔴 火枪手 -1` |
| **重大伤亡** | 单次攻击造成 ≥ 阈值人死亡（阈值=max(4, 总人数×5%)），每窗口只保留击杀数最多的一条 | `💥 第 X.Xs，🔵 鹰炮一炮带走 🔴 火枪手 ×5！` |
| **半灭线** | 任一方剩余兵力首次 ≤ 50% | `⚠️ 🔴 已损失过半（剩 4/10），战况告急` |
| **终结** | 一方全灭 | `☠️ 第 X.Xs，🔵 长枪兵踏平最后一名敌兵` |

- "重大伤亡"比"首杀"更有冲击力，**两者都保留**（首杀负责开局气氛，重大伤亡负责高潮）
- 重大伤亡阈值 = `max(4, 总人数 × 5%)`，大规模对局自动提高门槛
- **每个 2 秒窗口内最多只发一条重大伤亡播报**（取该窗口内击杀数最多的一条），避免刷屏
- 重大伤亡和半灭线**可以同片段触发**（先发重大伤亡条，再发半灭线条）

### 8.4 沉默期填充（W4 决议）

> **背景**：连续多个 2 秒窗口零伤亡时，完全沉默会让群友以为机器人卡死。  
> 单兵种接近期短（4~5 秒），但**血厚单位**（如黑骑士 600HP、要塞 HP 几千）出现时，零伤亡可能持续 10 秒以上，必须有动静。

#### 触发规则

- 连续**第 2 个**零伤亡窗口起，发一条**填充消息**（注意：第 1 个零伤亡窗口仍保持沉默，避免吵）
- 之后每 2 个零伤亡窗口发一次（即每 4 秒一条），直到出现伤亡为止
- 填充消息**不 sleep**（与零伤亡窗口共用，不打断节奏）

#### 填充消息选词（按战况随机一句）

**接近期**（双方都在移动靠近）：
- `⏳ 双方仍在接近，剑拔弩张...`
- `⏳ 战鼓未响，杀机已生`
- `⏳ 红蓝双方逐渐靠近射程`

**对耗期**（双方都在攻击但都没死，典型血厚单位互殴）：
- `⏳ 双方激烈交火，暂无伤亡`
- `⏳ 装甲互啃，子弹打在肉身上像挠痒...`（皮一下）
- `⏳ 互相伤害中，HP 缓慢下降`
- `⏳ 重甲单位的较量，比的就是耐心`

**僵持期**（HP 都低于 30%）：
- `⏳ 双方都已残血，下一击可能就是终结`
- `⏳ 鏖战至此，胜负只在一念之间`

#### 实现要点

- 模拟器在事件流里给每个 tick 标注当前**战况阶段**（接近 / 对耗 / 僵持），由播报层据此选词
- 阶段判定（基于事件流统计，**不是**实时 HP）：
  - 接近期：尚无任何攻击事件
  - 僵持期：双方剩余 HP 比例都 < 30%
  - 对耗期：以上之外
- 同一阶段内的话术池**不重复抽**（避免连发两条一样的），抽完池子重置

### 8.5 动态选词（W7：按伤害分类）

击杀播报术语**根据实际攻击模式 + 伤害类型 + 单位标签**选词，不再按单位类型标签分类。

#### 分类维度

| 分类 key | 条件 | 术语风格 | 示例单位 |
|---|---|---|---|
| `ranged_gunpowder` | 远程 + Ranged伤害 + Gunpowder标签 | 枪炮 | 火枪手、龙骑兵 |
| `ranged_archer` | 远程 + Ranged伤害 + Archer标签 | 弓箭 | 长弓手、弓骑兵 |
| `ranged_normal` | 远程 + Ranged伤害 + 兜底 | 通用射击 | 休伦木盾等 |
| `ranged_siege_art` | 远程 + Siege伤害 + Artillery标签 | 大炮 | 鹰炮、臼炮 |
| `ranged_siege` | 远程 + Siege伤害 + 兜底 | 爆破/投掷 | 掷弹兵、骑马掷弹兵 |
| `melee_hand` | 近战 + Hand伤害 + 兜底 | 冷兵器 | 长枪兵、黑骑士 |
| `melee_siege` | 近战 + Siege伤害 | 火攻 | 沙漠突袭者 |

#### 判定流程

1. 从 DEATH 事件取 `killer_attack_mode`（ranged/melee/ranged_penalized）和 `killer_damage_type`（Ranged/Siege/Hand）
2. 先按攻击模式分：ranged 系 vs melee 系
3. 再按伤害类型分：Ranged / Siege / Hand
4. 最后用单位标签辅助细分（Gunpowder / Archer / Artillery）
5. 每层都有兜底，不会漏

#### 死亡数档位（每类共用）

| 死亡数 | 档位 key |
|---|---|
| 1 | `"1"` |
| 2~3 | `"2-3"` |
| 4+ | `"4+"` |

- 窗口内同一方多次攻击合并成一条播报（不要每次攻击单发，太碎）
- 词库写在 `phrases.py` 常量文件里，方便调整不动逻辑

#### 阵型 emoji（独立于术语系统）

阵型面板中的 emoji 仍按单位类型标签判定（不变），但优先级调整为：
**Ship > Elephant > Camel > Cavalry > Artillery/Siege trooper > 步兵细分 > 兜底**

骑兵标签优先于 `Siege trooper`，避免草原骑兵等被误显示为 💣。

#### 战前角色卡

配兵摘要按 §3.9 取当前阵型里优先级最高的最多两条。拆建筑攻击排进这两条就显示，不再因为攻城槽而整段藏掉。

### 8.6 最终战报 + 结算（一起发，W3）

> **2026-09-23 更新**：当前最终战报与押注结算**分开发送**，顺序为“回放视频 → 最终战报 → 押注结算”。
> 无押注时不发送结算；没有视频生成成功时仍发送文字战报。

**单兵种战报示例：**

```
🏆 ━━━ 战斗结果 ━━━

战斗时长：47.3 秒

🔴 红方 全军覆没
  · 火枪手 ×10 → 0

🔵 蓝方 残兵
  · 长枪兵 ×6（损失 2/8）

🎖 MVP：🔵 长枪兵 #3
   伤害 287 / 击杀 4 / 综合分 343.5

━━━ 押注结算 ━━━
押对：@张三 @李四 @王五（3 人）
每人 +5 金币
押错：6 人，每人 -5 金币
全员参与奖：+1 金币
```

**多兵种战报示例：**

```
🏆 ━━━ 战斗结果 ━━━
胜方：🔵 蓝方（2号）
战斗时长：38.7 秒

🔴 红方 全军覆没
  · 黑骑士 ×2 → 0
  · 火枪手 ×11 → 0

🔵 蓝方 残兵
  · 铁甲舰 ×1（存活，HP 1847/3000）
  · 火枪手 ×4（损失 3/7）
  · 散兵 ×12（损失 4/16）

🎖 MVP：🔵 铁甲舰 #1
   伤害 1520 / 击杀 6 / 综合分 1060

━━━ 押注结算 ━━━
押对：@张三 @李四（2 人）
每人 +5 金币
押错：3 人，每人 -5 金币
全员参与奖：+1 金币
```

#### MVP 评选

- **综合分 = 伤害 × 0.5 + 击杀 × 50**
  - 让"补刀王"（高击杀低伤害）和"输出王"（高伤害低击杀）都有机会
  - 系数可在常量配置里调
- 平局时按伤害排序作为 tiebreaker
- MVP 限胜方（败方再 MVP 也无意义）

#### 押注结算
- 押对玩家**点名**（@形式）；超过 5 人时显示前 5 + "等 N 人"
- 平局退还入场券，不评 MVP（双方都没赢）

### 2026-05-21 追加决议（黑名单乱斗模式封板，详见 §2.4）

> 起因：`BATTLE_BLACKLIST` 池子已就位（21 个候选），群友催着"想玩怪物互殴"。把预研 §9.1 推进为正式设计。
> 设计哲学：**节目效果优先于公平**。

- ✅ **新增 `GameMode(id="blacklist")`**：在 `aoe3_battle/game.py` 注册，公开模式名为 `乱斗`。
  `game_launcher` 解析 `@bot 斗蛐蛐 乱斗` 即可触发
- ✅ **押注 / 战斗 / 结算流程完全复用模式 A**：押注1 / 押注2 / 开战 / 5 金币入场券 / 战报 + MVP 一条龙
- ✅ **战力分公式**（实现在 `lineup.py :: power_score`）：
  `HP_eff × DPS_eff`，其中 `HP_eff = HP / (1 - max_armor)`、
  `DPS_eff = max(dps_ranged × aoe_mult, dps_melee × aoe_mult)`、
  `aoe_mult = 1 + aoe_radius × 0.3`
  - **不计 `attack_siege`**：是 BuildingAttack 槽，模拟器不读（§3.9）
  - **不计倍率（multipliers）**：克制天然在战斗里发挥作用，避免加特林骆驼之类 ×100 倍率爆表
  - **不计 speed / 射程**：1v1 模拟里影响小且难量化
- ✅ **目标战力分锚定每方独立 `min × r`**（既不是 `max × r`，也不是全局 `min × r`！）：
  `red_target = min(red_scores) × r`，`blue_target = min(blue_scores) × r`，
  其中 `r ~ U(3.0, 6.0)`
  - **为什么用 min**：池内战力分跨度约 **360 万倍**（垮盛顿 80 亿 vs 民兵 2.8k），
    用 `max × r` 会让弱方堆几万个个体，模拟器跑爆
  - **为什么用本方独立 min**：用全局 min 时，若任一方抽到弱酋长（双月/民兵），
    target 锚到 11k，让另一方的英雄（曼苏尔/大名）被压成"1 只保底"——
    出现"3 双月 vs 1 曼苏尔"这种数量悬殊不好看。本方独立后变 5v5
  - `r` 即"本方最弱兵出兵数"。范围 3~6：避开 r=8 时节奏拖太长
